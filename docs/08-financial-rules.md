
# ۰۸ — قواعد محاسبات مالی

> این سند **قرارداد** است. هر فرمولی در پروژه باید از `packages/shared/src/money` و
> `packages/shared/src/financial` بیاید. بازنویسی فرمول در کامپوننت، کوئری SQL یا قالب
> گزارش ممنوع است — این مهم‌ترین اقدام کاهش ریسک R1 است.

## ۱. واحد و نوع

| موضوع | قرارداد |
|---|---|
| واحد پول | **ریال**، بدون استثنا. هیچ تبدیل خودکار به تومان در هیچ لایه‌ای. |
| نوع در دیتابیس | `BIGINT` (ریال صحیح). هرگز `NUMERIC`، `REAL` یا `DOUBLE`. |
| نوع در TypeScript | `bigint` با برند `Money` |
| نوع در JSON API | **رشته عددی** مثل `"125000000"`. هرگز `number`. |
| کسر ریال | وجود ندارد. هر نتیجه محاسبه به ریال صحیح گرد می‌شود. |
| درصد (نرخ مالیات) | عدد صحیح **basis point**: ۹٪ = `900`، ۱۰٪ = `1000`، ۹٫۵٪ = `950` |
| تعداد / مقدار | `NUMERIC(18,3)` در دیتابیس؛ در TS به‌صورت `bigint` مقیاس‌شده در هزارم |

```ts
export type Money = bigint & { readonly __brand: 'Money' };
export type Qty   = bigint & { readonly __brand: 'Qty' };   // مقیاس ۱۰۰۰
export type RateBp = number & { readonly __brand: 'RateBp' }; // عدد صحیح
```

### چرا `bigint` و نه کتابخانه decimal

مبالغ ریالی **صحیح** هستند و کسر ندارند. با `bigint` بومی:
بدون وابستگی اضافه، بدون سرریز، و تنها نقطه‌ای که دقت می‌تواند از دست برود مرز
سریالایز JSON است که با رشته بسته می‌شود. ([ADR-0003](adr/ADR-0003-money-bigint-rial.md))

## ۲. سیاست گرد کردن — قابل تنظیم و snapshot‌شده

طبق تصمیم Q3، سیاست گرد کردن **در تنظیمات مالی قابل تغییر** است:

```ts
export interface RoundingPolicy {
  scope: 'LINE' | 'INVOICE';                // محل گرد کردن
  mode: 'HALF_UP' | 'FLOOR' | 'HALF_EVEN';  // جهت گرد کردن
}
// پیش‌فرض سازمان: { scope: 'LINE', mode: 'HALF_UP' }

/** تنها تابع گرد کردن پروژه */
export function roundDiv(numerator: bigint, denominator: bigint, mode: RoundingMode): bigint;
```

قواعد:

1. **تنها یک تابع گرد کردن** در کل پروژه وجود دارد؛ تابع دوم با قاعده lint ممنوع است.
2. سیاست **پارامتر صریح** هر تابع محاسبه است و از متغیر سراسری خوانده نمی‌شود:
   ```ts
   calculateLine(input: LineInput, policy: RoundingPolicy): LineResult
   ```
   فراموش کردن آن یک **خطای کامپایل** است، نه یک باگ خاموش.
3. گرد کردن مجدد روی مقدار گرد‌شده ممنوع است (double rounding).
4. در حالت `scope: 'INVOICE'`، مالیات یک‌بار روی جمع خالص فاکتور محاسبه و به ردیف‌ها
   **تخصیص** داده می‌شود؛ تخصیص باید جمع‌شونده باشد (باقیمانده به بزرگ‌ترین ردیف) تا
   جمع ستون با جمع فاکتور بخواند.

> ⚠️ **سیاست روی خود سند snapshot می‌شود و با ثبت نهایی قفل می‌گردد.** تغییر تنظیمات
> سازمان، مبالغ اسناد گذشته را **تغییر نمی‌دهد**. این مهم‌ترین پیامد پاسخ Q3 است —
> ریسک R14 و [ADR-0012](adr/ADR-0012-rounding-policy-snapshot.md).

## ۳. محاسبه ردیف فاکتور

```
gross   = roundDiv(qtyMilli × unitPrice, 1000, policy.mode)
net     = gross − discount
tax     = حالت PERCENT:  roundDiv(net × rateBp, 10000, policy.mode)
          حالت AMOUNT :  مقدار واردشده کاربر
total   = net + tax
```

مثال با نرخ پیش‌فرض **۱۰٪** (`rateBp = 1000`) و سیاست پیش‌فرض (`LINE` + `HALF_UP`):

| تعداد | مبلغ واحد | مبلغ کل | تخفیف | خالص | مالیات | نهایی |
|---|---|---|---|---|---|---|
| ۳ | ۱٬۲۵۰٬۰۰۰ | ۳٬۷۵۰٬۰۰۰ | ۰ | ۳٬۷۵۰٬۰۰۰ | ۳۷۵٬۰۰۰ | ۴٬۱۲۵٬۰۰۰ |
| ۲٫۵ | ۱٬۰۰۰٬۰۰۱ | ۲٬۵۰۰٬۰۰۳ (گرد از ۲٬۵۰۰٬۰۰۲٫۵) | ۳ | ۲٬۵۰۰٬۰۰۰ | ۲۵۰٬۰۰۰ | ۲٬۷۵۰٬۰۰۰ |
| ۱ | ۱٬۰۰۰ | ۱٬۰۰۰ | ۱٬۰۰۰ | ۰ | ۰ | ۰ |

## ۴. قواعد اعتبارسنجی

| قاعده | رفتار در صورت نقض |
|---|---|
| `qty > 0` | رد با پیام «تعداد باید بزرگ‌تر از صفر باشد» |
| `unitPrice >= 0` | رد |
| `discount >= 0` | رد |
| `discount <= gross` | رد (پیش‌فرض). با تنظیم `allowDiscountOverGross` قابل باز کردن است؛ پیش‌فرض **بسته**. |
| `net >= 0` | رد — مبلغ خالص هرگز منفی نمی‌شود |
| `tax >= 0` | رد |
| `rateBp` در حالت `PERCENT` موجود و در بازه `[0, 10000]` | رد |
| `rateBp` در حالت `AMOUNT` باید `NULL` باشد | رد |
| تطبیق مقادیر ذخیره‌شده با بازمحاسبه | `422 FINANCIAL_MISMATCH` با مسیر فیلد — **بدون تصحیح خودکار** |

ردیف ناقص (شرح خالی یا تعداد صفر) **ذخیره نمی‌شود**؛ خطا در همان ردیف جدول نمایش داده
می‌شود، نه به‌صورت پیام کلی بالای فرم.

## ۵. مالیات: دو حالت صریح

| | حالت `PERCENT` | حالت `AMOUNT` |
|---|---|---|
| ورودی کاربر | نرخ درصد | مبلغ ریالی مالیات |
| `tax_rate_bp` | ثبت می‌شود | `NULL` |
| `tax_amount` | محاسبه می‌شود | همان مقدار کاربر |
| با تغییر تعداد/مبلغ/تخفیف | **بازمحاسبه می‌شود** | **دست‌نخورده می‌ماند** |
| نمایش در UI | «۹٪ (محاسبه‌شده)» | «مبلغ دستی» + نرخ مؤثر محاسبه‌شده به‌صورت اطلاعاتی |

رفتار مبهم‌زدا (الزام صریح §۱۲ پرامپت): اگر کاربر مالیات را **دستی** وارد کرده باشد و
سپس تعداد یا مبلغ واحد را تغییر دهد، مقدار دستی **بازنویسی نمی‌شود**. در عوض:

- نشان «مبلغ دستی» روی سلول مالیات باقی می‌ماند.
- اگر نرخ مؤثر از نرخ پیش‌فرض فاصله معنادار بگیرد، یک هشدار نرم نمایش داده می‌شود.
- یک اقدام صریح «بازگشت به حالت درصدی» وجود دارد که تنها راه بازنویسی است.

### نرخ پیش‌فرض

**نرخ جاری سازمان: ۱۰٪ (`rateBp = 1000`)** — طبق پاسخ Q4.

این مقدار به‌عنوان **داده مرجع** در `tax_rates` با کلید سال مالی seed می‌شود، نه در کد.
دست کاربر کاملاً باز است:

- می‌تواند برای هر ردیف یا فاکتور **درصد متفاوتی** وارد کند (حالت `PERCENT`).
- می‌تواند **مستقیم مبلغ** مالیات را وارد کند (حالت `AMOUNT`).
- می‌تواند مالیات را صفر کند.

نرخ پیش‌فرض فقط مقدار **اولیه فرم** است و هیچ محدودیتی ایجاد نمی‌کند.
**هیچ نرخ قانونی در کد hardcode نمی‌شود**؛ تغییر نرخ در آینده یک ردیف جدید در
`tax_rates` است، نه یک تغییر کد. نرخ هر ردیف در `tax_rate_bp` همان ردیف ذخیره می‌شود،
پس تغییر نرخ سازمان مبالغ اسناد گذشته را عوض نمی‌کند.

## ۶. محاسبه فاکتور بر اساس نوع

| `kind` | `gross` | `discount` | `tax` |
|---|---|---|---|
| `NORMAL` / `STAD` | Σ `items.gross` | Σ `items.discount` | Σ `items.tax` |
| `UTILITY` | `base_amount` | تخفیف فاکتور | طبق حالت مالیات فاکتور |
| `FUEL` | Σ `fuel_entries.amount` | ۰ (پنهان در فرم) | ۰ (پنهان در فرم) |

طبق پاسخ Q10، ستون‌های تخفیف و مالیات برای فاکتور سوخت **در مدل داده وجود دارند** ولی در
فرم پنهان و صفر هستند. اگر بعداً نیاز واقعی اعلام شود، نمایش آن‌ها یک تغییر پیکربندی
نوع فاکتور است، نه migration.

در همه حالت‌ها: `net = gross − discount` و `total = net + tax`.

## ۷. محاسبه سند

```
document.total_gross    = Σ invoices.gross_amount
document.total_discount = Σ invoices.discount_amount
document.total_net      = Σ invoices.net_amount
document.total_tax      = Σ invoices.tax_amount
document.total_amount   = Σ invoices.total_amount
```

به‌همراه این اتحاد که باید همیشه برقرار باشد و در تست تطبیق بررسی می‌شود:

```
document.total_amount = document.total_net + document.total_tax
```

## ۸. تجمیع گزارش مالیات (بر اساس فروشنده)

کلید گروه‌بندی: `invoices.vendor_id`.

طبق پاسخ **Q1 (گزینه الف)**، فروشنده روی **همه** انواع فاکتور در دسترس و **اختیاری** است.
تصویر مرجع این را تأیید می‌کند: ردیف اول گزارش یک فاکتور انشعابات با فروشنده
«شرکت توزیع برق» و نوع کالای «انشعاب برق» است.

فاکتور بدون فروشنده طبق تنظیم قالب یا از گزارش کنار گذاشته می‌شود یا در ردیف
«بدون فروشنده» تجمیع می‌گردد؛ پیش‌فرض: **کنار گذاشتن، با نمایش هشدار شمارش‌شده** در
پیش‌نمایش گزارش تا کاربر متوجه شود چند فاکتور در گزارش نیامده‌اند.

دامنه تجمیع (یک سند یا یک فصل از سال) به پاسخ **Q13** وابسته است؛ منطق تجمیع در هر دو
حالت **یکسان** است و فقط شرط کوئری فرق می‌کند.

برای هر فروشنده در یک سند:

| ستون گزارش | فرمول |
|---|---|
| مبلغ کالا | Σ `invoices.gross_amount` (**قبل** از تخفیف) |
| تخفیف | Σ `invoices.discount_amount` |
| مبلغ خالص | مبلغ کالا − تخفیف |
| عوارض و مالیات بر ارزش افزوده | Σ `invoices.tax_amount` |
| جمع کل | مبلغ خالص + مالیات |
| شماره صورتحساب | اگر `count(invoices) == 1` → همان شماره؛ اگر `> 1` → **خالی** |
| تاریخ صورتحساب | `invoice_date` **اولین** فاکتور پس از مرتب‌سازی صعودی `(invoice_date, id)` |
| اطلاعات هویتی فروشنده | از `vendor_snapshots` همان فاکتورها، نه از `vendors` زنده |

اتحادهایی که تست مستقل دارند:

1. `Σ rows.total == Σ document.invoices.total_amount` (برای فاکتورهای مشمول گزارش) —
   هیچ فاکتور یا ردیفی **دو بار شمرده نمی‌شود**.
2. `row.net == row.goods − row.discount` برای هر ردیف.
3. `row.total == row.net + row.tax` برای هر ردیف.
4. اگر فروشنده دو فاکتور با **تاریخ برابر** دارد، تاریخ انتخابی قطعی و تکرارپذیر است
   (ترتیب ثانویه `id`).
5. فروشنده با یک فاکتور ← شماره صورتحساب پر؛ با دو فاکتور ← خالی.

## ۹. قرارداد سریالایز BIGINT

خطر: `JSON.stringify` روی `bigint` خطا می‌دهد و `Number(bigint)` بالای ۲⁵³ دقت از دست
می‌دهد (ریسک R2). قرارداد:

**سمت سرور**

- یک `BigIntSerializerInterceptor` سراسری همه `bigint`ها را به رشته تبدیل می‌کند.
- `NUMERIC` تعداد به‌صورت رشته (`"2.500"`) منتقل می‌شود، نه `number`.
- Swagger این فیلدها را `type: string, pattern: ^-?\d+$` مستند می‌کند.

**سمت کلاینت**

- Zod schema مشترک: `z.string().regex(/^-?\d+$/).transform(BigInt)` → مقدار همیشه `bigint`.
- ورودی مبلغ (`CurrencyInput`) مقدار را به‌صورت رشته رقمی نگه می‌دارد و هرگز از
  `parseInt`/`Number`/`valueAsNumber` استفاده نمی‌کند.
- نمایش با `Intl.NumberFormat('fa-IR')` روی رشته گروه‌بندی‌شده؛ مقدار واقعی هرگز فارسی نمی‌شود.
- قاعده ESLint: فراخوانی `Number(`، `parseInt(`، `parseFloat(`، `+x` روی مقادیر برند
  `Money`/`Qty` خطا است.

**تست اجباری:** عبور رفت‌و‌برگشت مبلغ `9007199254740993` (یعنی ۲⁵³+۱) از فرم → API →
دیتابیس → گزارش، با مقدار **بیت‌به‌بیت یکسان**.
