
# ۱۲ — سیاست مدیریت فایل و اسکن‌ها

## ۱. محل ذخیره

object storage سازگار با S3 ([ADR-0011](adr/ADR-0011-s3-object-storage.md)):
SeaweedFS در توسعه، MinIO یا سرویس S3 سازمان در production (دلیل جایگزینی در
[ADR-0011](adr/ADR-0011-s3-object-storage.md) §«انحراف محیط توسعه»).

- bucket **خصوصی**؛ هیچ دسترسی عمومی و هیچ آدرس قابل حدس.
- فایل‌ها **خارج** از مسیر سرو وب برنامه قرار دارند؛ وب‌سرور هرگز مستقیم فایلی از این
  فضا سرو نمی‌کند.
- کلید شیء **سروری** ساخته می‌شود و نام کاربر در آن نیست:

```
documents/{documentId}/{attachmentId}.{ext}
reports/{reportRunId}.{ext}
```

نام اصلی فایل فقط در `attachments.original_filename` به‌عنوان **داده** ذخیره می‌شود و
هرگز در مسیر فایل‌سیستم یا کلید شیء استفاده نمی‌شود → مسیر Path Traversal بسته است.

## ۰.۵ چه کسی بارگذاری می‌کند

**کارپردازی و بایگانی، هر دو.** تا مدتی فقط بایگانی مجوز `attachment:upload` داشت؛
ولی اسکن فاکتورها دست کسی است که سند را ساخته، و نداشتن این مجوز یعنی او باید برای
هر پیوست منتظر کس دیگری بماند.

تفکیک وظایف سر جایش است، فقط مرزش دقیق‌تر شد:

| کار | کارپردازی | بایگانی |
|---|---|---|
| دیدن و دانلود پیوست | ✓ | ✓ |
| بارگذاری پیوست | ✓ | ✓ |
| حذف پیوست | — | ✓ |
| ثبت شماره و تاریخ سند | — | ✓ |

گذاشتن یک فایل برگشت‌پذیر است؛ برداشتنش نه. همان مرز، در آزمون
`role-separation.test.ts` پین شده است.

## ۰.۶ نمایشگر فایل

نمایشگر **تمام‌صفحه** است. یک اسکن A4 در یک کادر ۵۶rem خوانا نیست؛ کاربر یا باید
زوم کند و دنبال متن بگردد، یا فایل را دانلود کند و از سامانه بیرون برود.

| قالب | نمایشگر | امکانات |
|---|---|---|
| PDF | pdf.js | زوم، شمارهٔ صفحه، رندر پنجره‌ای |
| تصویر | `<img>` | زوم، جابه‌جایی با کشیدن |
| بقیه (مثل TIFF) | — | پیام صریح و دانلود |

**چرا pdf.js و نه `<iframe>`**: نمایشگر داخلی مرورگر در قاب، نه زوم قابل کنترل
می‌دهد نه شمارهٔ صفحه، و در هر مرورگر چیز دیگری است. ضمن اینکه سرویس API هدر
`frame-ancestors 'none'` می‌فرستد و هیچ پاسخی از آن داخل قاب نمی‌نشیند — همان
محدودیتی که پیش از این، پیش‌نمایش PDF را به یک راه‌حل `blob:` کشانده بود.

**رندر پنجره‌ای، نه یک‌جا.** یک اسکن ۲۰۰ صفحه‌ای اگر یک‌جا رندر شود، دویست بوم
تمام‌اندازه در حافظه می‌ماند و مرورگر چند ثانیه قفل می‌کند. اینجا جای هر صفحه از
ابتدا رزرو می‌شود (اندازه‌اش را pdf.js بدون رندر هم می‌دهد، پس نوار اسکرول از همان
اول درست است) ولی فقط صفحه‌های نزدیک به دید رندر می‌شوند و با دور شدن، بومشان آزاد
می‌شود. حافظه ثابت می‌ماند، مستقل از تعداد صفحه.

خود کتابخانه هم **تنبل** بارگذاری می‌شود: ۳۳۰ کیلوبایت pdf.js نباید روی اولین
بارگذاری سامانه بنشیند، وقتی فقط هنگام باز کردن یک PDF لازم است.

## ۲. فراداده در دیتابیس

فراداده و مالکیت فایل در `attachments` داخل **همان تراکنش** عملیات مربوطه ثبت می‌شود، تا
فایل بی‌صاحب یا رکورد بی‌فایل باقی نماند:

1. رکورد `attachments` با وضعیت `PENDING` ایجاد می‌شود.
2. فایل آپلود و اعتبارسنجی می‌شود.
3. وضعیت به `READY` تغییر می‌کند و به سند متصل می‌شود.
4. job پاک‌سازی، رکوردهای `PENDING` کهنه و اشیاء بی‌رکورد را حذف می‌کند.

## ۳. اعتبارسنجی آپلود

| کنترل | مقدار پیش‌فرض (قابل تنظیم) |
|---|---|
| allowlist نوع | `application/pdf`, `image/jpeg`, `image/png`, `image/tiff` |
| **ممنوع** | `svg`, `html`, `xml`, هر نوع اجرایی یا آرشیو |
| حجم هر فایل | ۲۰ مگابایت |
| تعداد فایل هر سند | ۳۰ |
| حجم کل هر سند | ۲۰۰ مگابایت |
| بررسی نوع واقعی | magic byte با پیاده‌سازی خودیِ `packages/shared/src/files/file-types.ts` — **MIME اعلامی کافی نیست** |
| نام فایل | از latin1 به UTF-8 برگردانده می‌شود (`decodeMultipartFilename`)؛ وگرنه نام فارسی مخدوش ذخیره می‌شود |
| ناسازگاری MIME اعلامی و واقعی | **رد** با پیام روشن |
| checksum | SHA-256 ذخیره می‌شود (تشخیص تکراری و صحت) |
| بدافزار | رابط `VirusScanner` قابل اتصال؛ ClamAV در صورت وجود زیرساخت. `scan_status`: `SKIPPED`/`CLEAN`/`INFECTED` |
| فایل آلوده | قرنطینه و عدم اتصال به سند؛ ثبت رویداد امنیتی |

> **وضعیت پیاده‌سازی (فاز ۵):** تشخیص نوع، ناسازگاری MIME، سقف‌ها، checksum و تشخیص
> تکراری ساخته و آزمون شده‌اند. استخراج تعداد صفحه PDF و اتصال `VirusScanner` هنوز
> انجام نشده‌اند؛ `scan_status` فعلاً همیشه `SKIPPED` است. فهرست انواع مجاز عمداً
> دقیقاً چهار نوع است و با کتابخانه عمومی `file-type` کار نمی‌کند: هر نوعِ شناخته‌شده
> یک تصمیم آگاهانه است، نه یک قابلیتِ همراه کتابخانه.

## ۴. دانلود و پیش‌نمایش

- دانلود **فقط** از endpoint مجوزدار: `GET /api/v1/attachments/:id/content`.
- بررسی‌ها پیش از استریم: مجوز `attachment:read` + دامنه دسترسی همان سند برای آن نقش.
- هدرها: `Content-Disposition: attachment; filename*=UTF-8''…`,
  `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`.
- `Content-Type` از **نوع تشخیص‌داده‌شده** سرور می‌آید، نه از ورودی کاربر.
- پیش‌نمایش تصویر مستقیم از همان endpoint؛ پیش‌نمایش PDF از روی `blob:` در origin خود
  برنامه.
  **چرا PDF از راه blob:** سرویس API هدر `Content-Security-Policy: frame-ancestors 'none'`
  می‌فرستد، پس هیچ پاسخی از آن — حتی هم‌مبدأ — داخل `<iframe>` نمی‌نشیند
  (`net::ERR_BLOCKED_BY_RESPONSE`). هدر ضعیف نشد؛ بایت‌ها با `fetch` هم‌مبدأ خوانده و به
  `blob:` تبدیل می‌شوند که به خود صفحه تعلق دارد. object URL هنگام بسته شدن پیش‌نمایش
  آزاد می‌شود.
  نمایشگر داخلی PDF مرورگر استفاده می‌شود؛ `pdf.js` با worker محلی (پیمایش، بزرگ‌نمایی،
  چرخش) **هنوز اضافه نشده است**.
- اگر فایل قابل پیش‌نمایش نباشد، **خطای صریح و قابل فهم** نمایش داده می‌شود، نه کادر خالی
  (الزام §۳۶ پرامپت).
- فایل آپلودی هرگز در `<iframe>` بدون sandbox یا با `srcdoc` بارگذاری نمی‌شود.

## ۵. حذف و تاریخچه

- حذف از UI = `deleted_at` (تنها soft-delete پروژه، با معنای عملیاتی روشن).
- حذف یا جایگزینی فایل مجوز `attachment:delete` می‌خواهد و تا پیش از نهایی شدن بایگانی
  مجاز است.
- هر عملیات فایل (آپلود، مشاهده، دانلود، حذف) در `audit_logs` ثبت می‌شود.
- حذف فیزیکی شیء طبق سیاست retention و با job جداگانه — نه همزمان با حذف منطقی، تا
  بازگشت ممکن باشد.

## ۶. خروجی‌های تولیدشده (PDF/Excel)

- در همان object storage با پیشوند `reports/` ذخیره می‌شوند.
- `report_runs.expires_at` مهلت نگهداری دارد؛ job دوره‌ای فایل منقضی را حذف می‌کند.
- دانلود فقط توسط `requested_by` یا دارنده `report:read_history`.
- لینک دانلود **بدون** توکن در URL؛ مجوز از نشست می‌آید. (داده حساس در URL ممنوع)

## ۷. پشتیبان‌گیری (جزئیات در فاز ۹)

- دیتابیس و object storage **هر دو** پشتیبان‌گیری می‌شوند و پشتیبان آن‌ها باید
  **هم‌زمان‌پذیر** باشد؛ سند بدون اسکنش یا اسکن بدون سندش بی‌ارزش است.
- backup رمزنگاری‌شده و با دسترسی محدود.
- **تست بازیابی واقعی** در محیط کنترل‌شده؛ وجود فایل backup به‌تنهایی پذیرفته نیست.
- سیاست retention با نیاز قانونی نگهداری اسناد سازمان هم‌راستا می‌شود (نیازمند ورودی شما).
