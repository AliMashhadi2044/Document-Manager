
# ۱۲ — سیاست مدیریت فایل و اسکن‌ها

## ۱. محل ذخیره

object storage سازگار با S3 ([ADR-0011](adr/ADR-0011-s3-object-storage.md)):
MinIO در توسعه، MinIO یا سرویس S3 سازمان در production.

- bucket **خصوصی**؛ هیچ دسترسی عمومی و هیچ آدرس قابل حدس.
- فایل‌ها **خارج** از مسیر سرو وب برنامه قرار دارند؛ وب‌سرور هرگز مستقیم فایلی از این
  فضا سرو نمی‌کند.
- کلید شیء **سروری** ساخته می‌شود و نام کاربر در آن نیست:

```
documents/{documentId}/{attachmentId}.{ext}
reports/{reportRunId}.{ext}
```

نام اصلی فایل فقط در `attachments.original_filename` به‌عنوان **داده** ذخیره می‌شود و
هرگز در مسیر فایل‌سیستم یا کلید شیء استفاده نمی‌شود → مسیر Path Traversal بسته است.

## ۲. فراداده در دیتابیس

فراداده و مالکیت فایل در `attachments` داخل **همان تراکنش** عملیات مربوطه ثبت می‌شود، تا
فایل بی‌صاحب یا رکورد بی‌فایل باقی نماند:

1. رکورد `attachments` با وضعیت `PENDING` ایجاد می‌شود.
2. فایل آپلود و اعتبارسنجی می‌شود.
3. وضعیت به `READY` تغییر می‌کند و به سند متصل می‌شود.
4. job پاک‌سازی، رکوردهای `PENDING` کهنه و اشیاء بی‌رکورد را حذف می‌کند.

## ۳. اعتبارسنجی آپلود

| کنترل | مقدار پیش‌فرض (قابل تنظیم) |
|---|---|
| allowlist نوع | `application/pdf`, `image/jpeg`, `image/png`, `image/tiff` |
| **ممنوع** | `svg`, `html`, `xml`, هر نوع اجرایی یا آرشیو |
| حجم هر فایل | ۲۰ مگابایت |
| تعداد فایل هر سند | ۳۰ |
| حجم کل هر سند | ۲۰۰ مگابایت |
| بررسی نوع واقعی | magic byte با `file-type` — **MIME اعلامی کافی نیست** |
| ناسازگاری MIME اعلامی و واقعی | **رد** با پیام روشن |
| checksum | SHA-256 ذخیره می‌شود (تشخیص تکراری و صحت) |
| بدافزار | رابط `VirusScanner` قابل اتصال؛ ClamAV در صورت وجود زیرساخت. `scan_status`: `SKIPPED`/`CLEAN`/`INFECTED` |
| فایل آلوده | قرنطینه و عدم اتصال به سند؛ ثبت رویداد امنیتی |

PDF: تعداد صفحه استخراج و ذخیره می‌شود؛ PDF دارای JavaScript یا فرم فعال علامت‌دار و در
پیش‌نمایش با `pdf.js` بدون اجرای اسکریپت رندر می‌شود.

## ۴. دانلود و پیش‌نمایش

- دانلود **فقط** از endpoint مجوزدار: `GET /api/v1/attachments/:id/content`.
- بررسی‌ها پیش از استریم: مجوز `attachment:read` + دامنه دسترسی همان سند برای آن نقش.
- هدرها: `Content-Disposition: attachment; filename*=UTF-8''…`,
  `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`.
- `Content-Type` از **نوع تشخیص‌داده‌شده** سرور می‌آید، نه از ورودی کاربر.
- پیش‌نمایش تصویر با `blob:` در همان origin؛ پیش‌نمایش PDF با `pdf.js` و worker محلی
  (پیمایش صفحات، بزرگ‌نمایی، چرخش).
- اگر فایل قابل پیش‌نمایش نباشد، **خطای صریح و قابل فهم** نمایش داده می‌شود، نه کادر خالی
  (الزام §۳۶ پرامپت).
- فایل آپلودی هرگز در `<iframe>` بدون sandbox یا با `srcdoc` بارگذاری نمی‌شود.

## ۵. حذف و تاریخچه

- حذف از UI = `deleted_at` (تنها soft-delete پروژه، با معنای عملیاتی روشن).
- حذف یا جایگزینی فایل مجوز `attachment:delete` می‌خواهد و تا پیش از نهایی شدن بایگانی
  مجاز است.
- هر عملیات فایل (آپلود، مشاهده، دانلود، حذف) در `audit_logs` ثبت می‌شود.
- حذف فیزیکی شیء طبق سیاست retention و با job جداگانه — نه همزمان با حذف منطقی، تا
  بازگشت ممکن باشد.

## ۶. خروجی‌های تولیدشده (PDF/Excel)

- در همان object storage با پیشوند `reports/` ذخیره می‌شوند.
- `report_runs.expires_at` مهلت نگهداری دارد؛ job دوره‌ای فایل منقضی را حذف می‌کند.
- دانلود فقط توسط `requested_by` یا دارنده `report:read_history`.
- لینک دانلود **بدون** توکن در URL؛ مجوز از نشست می‌آید. (داده حساس در URL ممنوع)

## ۷. پشتیبان‌گیری (جزئیات در فاز ۹)

- دیتابیس و object storage **هر دو** پشتیبان‌گیری می‌شوند و پشتیبان آن‌ها باید
  **هم‌زمان‌پذیر** باشد؛ سند بدون اسکنش یا اسکن بدون سندش بی‌ارزش است.
- backup رمزنگاری‌شده و با دسترسی محدود.
- **تست بازیابی واقعی** در محیط کنترل‌شده؛ وجود فایل backup به‌تنهایی پذیرفته نیست.
- سیاست retention با نیاز قانونی نگهداری اسناد سازمان هم‌راستا می‌شود (نیازمند ورودی شما).
