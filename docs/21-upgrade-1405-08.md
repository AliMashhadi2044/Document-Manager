# ۲۱ — راهنمای ارتقای نسخهٔ مستقر، بدون از دست رفتن داده

این سند **پیش از اجرا** خوانده می‌شود. مخاطبش کسی است که نسخهٔ در حال استفاده را
بالا می‌برد، روی پایگاه داده‌ای که داده‌های واقعی دارد.

خلاصهٔ یک‌خطی: **هیچ مهاجرتِ این نسخه داده‌ای را پاک یا بازنویسی نمی‌کند.** همهٔ
تغییرهای پایگاه داده افزایشی‌اند — سه ستون تازه با مقدار پیش‌فرض، هشت ایندکس، و
یک ستون بی‌استفاده که برداشته می‌شود.

---

## ۱. آنچه در پایگاه داده عوض می‌شود

| مهاجرت | کار | اثر روی داده موجود |
|---|---|---|
| `20261030090000_user_preferences_client_settings` | دو ستون `last_section` و `select_prefs` به `user_preferences` | هیچ؛ هر دو `NULL`پذیر |
| `20261030140000_drop_unused_dashboard_pref` | حذف ستون `dashboard` از `user_preferences` | ستون از روز اول نوشته نشده بود و هیچ کدی نمی‌خواندش |
| `20261105090000_base_data_defaults` | ستون `is_default` روی هفت فهرست پایه و `petty_cash_holders`، و ایندکس جزئی یکتا برای هرکدام | هیچ؛ مقدار پیش‌فرض `false` است و هیچ ردیفی عوض نمی‌شود |

**تنها حذفِ این نسخه** ستون `dashboard` است. اگر می‌خواهید محتاط‌تر باشید، پیش از
اجرا از همان جدول یک تصویر بگیرید:

```sql
CREATE TABLE user_preferences_backup_1405_08 AS TABLE user_preferences;
```

هیچ جدولی `DROP` نمی‌شود، هیچ ستونی نوع عوض نمی‌کند، و هیچ `UPDATE` انبوهی
اجرا نمی‌شود.

### ایندکس‌های یکتا — تنها جایی که مهاجرت می‌تواند **شکست بخورد**

برای هر فهرست یک ایندکس جزئی ساخته می‌شود: «حداکثر یک ردیف با `is_default = true`».
چون ستون تازه است و همه‌جا `false`، ساختنش روی داده موجود همیشه موفق است. اگر
مهاجرت را **دوبار** اجرا کنید، خطای «ایندکس از قبل هست» می‌گیرید، نه خرابی داده.

## ۲. ترتیب اجرا

```bash
# ۱. پشتیبان تازه — پیش از هر چیز، و روی همان پایگاه داده‌ای که ارتقا می‌یابد
npm run backup

# ۲. تصویر نسخهٔ تازه را بسازید (یا بکشید)
docker build -t document-manager:1405-08 .

# ۳. سرویس را متوقف کنید
#    دلیل: مهاجرت با سرویسِ در حال اجرا هم کار می‌کند، ولی چند ثانیه‌ای که
#    نسخهٔ قدیمی کد با شِمای تازه کار می‌کند، لازم نیست ریسکش را بپذیرید.
docker compose stop api

# ۴. مهاجرت
RUN_MIGRATIONS=true docker compose run --rm api node apps/api/dist/main.js --version
#    یا مستقیم:
npx prisma migrate deploy --schema apps/api/prisma/schema.prisma

# ۵. سرویس تازه را بالا بیاورید
docker compose up -d api

# ۶. سلامت
curl -fsS http://localhost:3100/api/v1/health
```

`RUN_SEED` را **لازم ندارید**: این نسخه دادهٔ مرجع تازه‌ای نمی‌خواهد. اجرای
دوباره‌اش هم بی‌خطر است (idempotent)، ولی کاری نمی‌کند.

### برگشت (rollback)

نسخهٔ قبلی کد با شِمای تازه **کار می‌کند**: ستون‌های تازه `NULL`پذیر یا
پیش‌فرض‌دارند و کد قدیمی سراغشان نمی‌رود. تنها استثنا `dashboard` است که کد
قدیمی هم نمی‌خواندش. پس برگشت یعنی فقط برگرداندن تصویر قبلی؛ نیازی به برگرداندن
پایگاه داده نیست.

## ۳. تغییرهای رفتاری که **بدون** مهاجرت‌اند — ولی باید بدانید

این‌ها داده را عوض نمی‌کنند، ولی از لحظهٔ استقرار دیده می‌شوند:

۱. **شرح فاکتور اجباری شد.** فاکتورهای قدیمیِ بدون شرح سرِ جایشان می‌مانند و
   گزارش‌ها دست‌نخورده‌اند؛ ولی اگر کاربر یکی از آن‌ها را **ویرایش** کند، تا شرح
   را پر نکند ثبت نمی‌شود. اگر می‌خواهید بدانید چند فاکتور چنین‌اند:

   ```sql
   SELECT count(*) FROM invoices WHERE description IS NULL OR btrim(description) = '';
   ```

۲. **تنخواه‌دار و نام صاحب حساب قبض اجباری شدند** (در همان فرم، برای روش‌های
   پرداختی که این فیلدها را دارند). همان قاعده: داده‌های گذشته دست‌نخورده، ولی
   ویرایششان این فیلدها را می‌خواهد.

۳. **گزارش مالیات، کد ملی را دیگر چهارتا‌چهارتا جدا نمی‌کند.** معیار، شکل خود
   عدد است: دوازده‌رقمی (شمارهٔ اقتصادی) گروه‌بندی می‌شود، ده و یازده‌رقمی
   (کد ملی و شناسهٔ ملی) نه. گزارش‌های قبلی که به‌صورت فایل گرفته شده‌اند عوض
   نمی‌شوند.

۴. **ترجیح‌های نمایشی کاربران از مرورگر به پروفایل منتقل شده‌اند.** کاربری که
   تم یا پین فهرست‌ها را قبلاً در همان مرورگر تنظیم کرده بود، نخستین بار پیش‌فرض
   را می‌بیند و باید یک‌بار دوباره انتخاب کند. این داده در `localStorage` بود و
   قابل انتقال نیست.

۵. **سقف نرخ درخواست فعال است.** اگر سرویس پشت proxy معکوس است، `TRUST_PROXY=true`
   را بگذارید؛ وگرنه همهٔ کاربران یک نشانی دیده می‌شوند و سقف زودتر از موعد
   می‌خورد. (`.env.example` را ببینید.)

## ۴. پس از استقرار — پنج دقیقه کار که ارزشش را دارد

این نسخه چند «پیش‌فرض» آورده که تا تنظیم نشوند، هیچ فرقی با قبل ندارند:

- **اطلاعات پایه → هر فهرست → ستون «پیش‌فرض»**: واحد اندازه‌گیریِ غالب (مثلاً
  «عدد»)، نوع انشعاب و نوع سوختِ رایج را علامت بزنید.
- **تنخواه‌داران**: تنخواه‌دار غالب را پیش‌فرض کنید.
- **فصل‌ها و انواع فاکتور → روش‌های پرداخت**: برای هر نوع فاکتور، روش پیش‌فرض را
  با دکمهٔ ★ انتخاب کنید (مثلاً «کارپرداز / تنخواه» برای فاکتور عادی).
- **فصل‌ها و انواع فاکتور → پیش‌فرض مالیات ردیف‌ها**: اگر فاکتورهایتان معاف‌اند،
  نرخ را صفر بگذارید.
- **فروشندگان**: برای فروشنده‌ای که چند شبا دارد، شبای غالب را پیش‌فرض کنید.

هیچ‌کدام اجباری نیستند؛ نبودنشان یعنی همان رفتار امروز.
