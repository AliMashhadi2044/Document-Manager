## ۲. کار دستی یکم: مجوز تازهٔ `security_settings:write`

مهلت بی‌تحرکی نشست حالا از رابط تنظیم می‌شود و مجوز خودش را دارد. تا این مجوز
به نقش مدیر سامانه نرسد، زبانهٔ «امنیت نشست» دیده نمی‌شود (و مسیرش ۴۰۳ می‌دهد).

دو راه هست و **راه دوم برای نسخهٔ مستقر امن‌تر است**:

### راه الف — اجرای seed مرجع

```bash
npm run db:seed -w @dm/api        # یا در Docker: RUN_SEED=true
```

> ⚠️ **هشدار مهم.** این اسکریپت تخصیص مجوزهای نقش‌ها را با **ماتریس پیش‌فرض کد**
> هم‌راستا می‌کند: مجوزهایی که در ماتریس نیستند از نقش **حذف** می‌شوند. اگر در
> «مدیریت کاربران ← نقش‌ها و دسترسی‌ها» دسترسی نقشی را دست‌کاری کرده‌اید، آن
> تغییر برمی‌گردد به حالت پیش‌فرض. پیش از اجرا یک تصویر بگیرید:
>
> ```sql
> CREATE TABLE role_permissions_backup_1405_08b AS TABLE role_permissions;
> ```
>
> و برای دیدن اینکه چه چیزی حذف خواهد شد، فهرست فعلی را نگه دارید:
>
> ```sql
> SELECT r.key AS role, p.key AS permission
> FROM role_permissions rp
> JOIN roles r ON r.id = rp.role_id
> JOIN permissions p ON p.id = rp.permission_id
> ORDER BY r.key, p.key;
> ```

### راه ب — فقط همین مجوز (بدون دست زدن به بقیه)

هر دو دستور idempotent‌اند؛ اجرای دوباره‌شان بی‌اثر است.

```sql
INSERT INTO permissions (id, key, group_key, title_fa)
VALUES (gen_random_uuid(), 'security_settings:write', 'security_settings',
        'مدیریت تنظیمات امنیتی نشست')
ON CONFLICT (key) DO NOTHING;
```

```sql
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.key = 'SYSTEM_ADMIN' AND p.key = 'security_settings:write'
ON CONFLICT DO NOTHING;
```

بررسی:

```sql
SELECT p.key, r.key AS role
FROM permissions p
LEFT JOIN role_permissions rp ON rp.permission_id = p.id
LEFT JOIN roles r ON r.id = rp.role_id
WHERE p.key = 'security_settings:write';
```

باید یک ردیف با `SYSTEM_ADMIN` برگردد. (اگر نقش دیگری هم باید این اختیار را
داشته باشد، از همان صفحهٔ «نقش‌ها و دسترسی‌ها» بدهید؛ از SQL لازم نیست.)

### مهلت نشست پس از ارتقا

`SESSION_IDLE_TTL_MINUTES` در `.env` از این پس فقط **پیش‌فرض** است. تا کسی از
رابط عددی نگذارد، همان مقدار محیطی حاکم است — یعنی رفتار امروز عوض نمی‌شود.
بازهٔ مجاز ۵ تا ۷۲۰ دقیقه است و کادر خالی، مهلت را برنمی‌دارد (پیش‌فرض محیطی
برمی‌گردد). هر تغییر در ردپای حسابرسی با عنوان `SESSION_POLICY_SET` می‌نشیند.

## ۳. کار دستی دوم: قالب‌های گزارش

سه قالب سیستمی عوض شده‌اند:

| گزارش | تغییر |
|---|---|
| صورت ریز هزینه‌های **جاری** | ستون «تاریخ صورت حساب» (فقط روی صفحه، در چاپ/PDF/HTML نمی‌آید) و ستون «پرداخت ذی‌نفع» که شد «پرداخت به» با واژه: کارپرداز / ذی‌نفع / کارپرداز و ذی‌نفع / قبض |
| صورت ریز هزینه‌های **عمرانی** | ستون «تاریخ صورت حساب» (فقط روی صفحه) |
| لیست هزینهٔ سوخت | امضای «مسئول کارپردازی» به‌صورت پیش‌فرض |

قالب سیستمی **داده** است، نه کد: تا seed اجرا نشود، این تغییرها در برنامه دیده
نمی‌شوند.

```bash
npm run db:seed -w @dm/api        # یا در Docker: RUN_SEED=true
```

نسخهٔ منتشرشدهٔ قبلی **ویرایش نمی‌شود**؛ نسخهٔ تازه‌ای منتشر می‌گردد و
خروجی‌های تاریخی به نسخهٔ خودشان بسته می‌مانند. پس گزارش‌هایی که قبلاً گرفته و
ذخیره شده‌اند عوض نمی‌شوند.

### ⚠️ تله: اگر قالب فعال، **کپیِ خودتان** باشد

seed فقط قالب **سیستمی** را به‌روز می‌کند. اگر از یک گزارش کپی گرفته‌اید و آن
کپی را قالب فعال کرده‌اید، seed به آن دست نمی‌زند و کاربر هیچ تغییری نمی‌بیند —
بدون هیچ خطایی. این را پیش از اجرا بسنجید:

```sql
SELECT t.key, d.name AS active_definition, d.is_system
FROM report_types t
LEFT JOIN report_definitions d ON d.id = t.active_definition_id
ORDER BY t.key;
```

هر ردیفی که `is_system = false` باشد، یعنی قالب فعالش کپیِ شماست. برای آن‌ها
تغییر را دستی ببرید:

۱. **طراح گزارش** → همان قالب فعال → **نسخهٔ پیش‌نویس تازه**.
۲. تغییرهای جدول بالا را روی آن اعمال کنید (ستون تاریخ با `screenOnly`، ستون
   «پرداخت به» با مقدار `row.payeeTitle`، امضای `PROCUREMENT_LEAD`).
۳. **انتشار**. تنظیم‌های خودتان (مثلاً تعداد ردیف خالی) دست‌نخورده می‌ماند.

ساده‌ترین مرجع برای کپی کردن مقادیر، همان قالب سیستمیِ تازه‌منتشرشده است که در
کنار کپی شما در فهرست دیده می‌شود.

## ۴. تغییر رفتاری: روش پرداخت در فاکتور الزامی شد

«ثبت نشود» دیگر یک حالت نیست. از لحظهٔ استقرار:

- **فاکتور تازه** بدون روش پرداخت ثبت نمی‌شود (سرور ۴۲۲ می‌دهد: «روش پرداخت
  فاکتور الزامی است»). این سمت **سرور** بررسی می‌شود، نه فقط در فرم.
- **فاکتورهای قدیمیِ بدون روش پرداخت** سر جایشان می‌مانند و گزارش‌ها دست‌نخورده‌اند.
  باز کردنشان هم کار می‌کند؛ فیلد خالی نشان داده می‌شود. ولی **ویرایش و ثبت**
  آن فاکتور تا انتخاب روش پرداخت انجام نمی‌شود، و قاعدهٔ ثبت نهایی هم
  سرِ جایش است: سندِ دارای چنین فاکتوری با پیام «روش پرداخت انتخاب نشده است»
  ثبت نهایی نمی‌شود (این بررسی از قبل بود و عوض نشده).

پیش از استقرار بشمارید با چند مورد روبه‌رویید:

```sql
SELECT d.status, count(*) AS invoices
FROM invoices i
JOIN financial_documents d ON d.id = i.document_id
LEFT JOIN invoice_payments p ON p.invoice_id = i.id
WHERE p.invoice_id IS NULL
GROUP BY d.status
ORDER BY 2 DESC;
```

و برای دیدن اینکه کدام‌ها هستند (تا به کارپردازی بگویید):

```sql
SELECT d.id AS document_id, d.title, d.status, i.id AS invoice_id, i.description
FROM invoices i
JOIN financial_documents d ON d.id = i.document_id
LEFT JOIN invoice_payments p ON p.invoice_id = i.id
WHERE p.invoice_id IS NULL
ORDER BY d.created_at;
```

اگر همه در وضعیت `DRAFT` یا `REOPENED` باشند (در محیط توسعه همین‌طور بود:
۱۱ پیش‌نویس و ۱ بازگشایی‌شده)، کار خاصی لازم نیست: هیچ سند ثبت‌شده‌ای
تحت‌تأثیر نیست و اصلاحشان با یک‌بار ویرایش انجام می‌شود. **هیچ اسکریپتِ پر کردن
خودکار ندهید**: روش پرداخت یک واقعیت مالی است و حدس زدنش یعنی نوشتن داده‌ای که
کسی تأیید نکرده.

## ۵. بقیهٔ تغییرهای رفتاری — بی‌نیاز از کار دستی

۱. **کد ملی با صفر ابتدایی، درست نمایش داده می‌شود.** پیش از این موتور گزارش
   رشتهٔ تمام‌رقمی را عدد می‌خواند و `0123456789` به `123456789` تبدیل می‌شد.
   داده در پایگاه داده همیشه درست بود؛ فقط نمایش خراب بود. گزارش‌هایی که
   قبلاً به‌صورت فایل گرفته شده‌اند عوض نمی‌شوند — در صورت نیاز دوباره بگیرید.

۲. **ردپای حسابرسی برای دو عمل، از این پس ثبت می‌شود.** `entity_id` ستونی از
   نوع UUID است و کلیدِ رشته‌ایِ تنظیم به آن می‌رفت؛ خطا بیرون از تراکنش فقط
   لاگ می‌شد و درخواست ۲۰۰ برمی‌گرداند. نتیجه این بود که `BASE_DATA_REORDER` در
   کل تاریخ پایگاه داده **صفر** ردیف داشت و تغییر پیش‌فرض مالیات سازمان هیچ
   ردی نمی‌گذاشت. حالا کلید در `entity_type` می‌نشیند. رخدادهای گذشته
   بازسازی‌شدنی نیستند.

۳. **صفحهٔ فصل‌ها دیگر با پاسخِ بدون «پیش‌فرض‌های فاکتور» از کار نمی‌افتد.** این
   حالت وقتی پیش می‌آمد که رابطِ تازه به سرویسِ قدیمی وصل می‌شد — یعنی دقیقاً
   در فاصلهٔ بین به‌روزرسانی دو سرویس. فقط اصلاح رابط است.

۴. **Tab از فهرست انتخابِ بازشده، داخل همان فرم می‌ماند.** مربوط به ترجیح
   «ظاهر و شخصی‌سازی ← فهرست‌های انتخاب با Tab ← با رسیدن فوکوس باز شود» است:
   پیش از این Tab کاربر را از فرم بیرون می‌انداخت و فوکوس سر از منوی کنار صفحه
   درمی‌آورد. ترجیح کاربران دست‌نخورده می‌ماند.

## ۶. ترتیب اجرا

```bash
# ۱. پشتیبان تازه — پیش از هر چیز
npm run backup

# ۲. وضعیت فعلی را بسنجید (بندهای ۳ و ۴ همین سند)
#    کدام قالب فعال، کپیِ کاربر است؟ چند فاکتور بدون روش پرداخت است؟

# ۳. تصویر نسخهٔ تازه
docker build -t document-manager:1405-08b .

# ۴. توقف سرویس
docker compose stop api

# ۵. مهاجرت — در این نسخه چیزی برای اجرا ندارد، ولی بی‌خطر و لازم است
npx prisma migrate deploy --schema apps/api/prisma/schema.prisma

# ۶. داده مرجع: مجوز تازه + نسخهٔ تازهٔ قالب‌های گزارش
#    هشدار بند ۲ را خوانده باشید (تخصیص مجوز نقش‌ها هم‌راستا می‌شود).
npm run db:seed -w @dm/api        # یا RUN_SEED=true در Docker

# ۷. بالا آوردن
docker compose up -d api

# ۸. سلامت
curl -fsS http://localhost:3100/api/v1/health
```

اگر نمی‌خواهید seed تخصیص نقش‌ها را دست بزند: مرحلهٔ ۶ را با **راه ب** بند ۲
جایگزین کنید — ولی توجه کنید که قالب‌های گزارش بند ۳ هم از همین seed می‌آیند.
در این صورت قالب‌ها را دستی از طراح گزارش به‌روز کنید.

### برگشت (rollback)

شِما عوض نشده، پس نسخهٔ قبلی کد با همین پایگاه داده **کار می‌کند**. دو نکته:

- مجوز تازه در پایگاه داده می‌ماند و بی‌اثر است؛ کد قدیمی سراغش نمی‌رود.
- نسخهٔ تازهٔ قالب‌های گزارش هم می‌ماند و کد قدیمی هم همان را اجرا می‌کند. اگر
  می‌خواهید گزارش به شکل قبلی برگردد، از طراح گزارش نسخهٔ قبلی را فعال کنید
  (نسخه‌های قدیمی حذف نشده‌اند).
- تنظیم `session_policy` در `system_settings` می‌ماند؛ کد قدیمی آن را نمی‌خواند
  و به `SESSION_IDLE_TTL_MINUTES` برمی‌گردد.

نیازی به برگرداندن پایگاه داده نیست.
