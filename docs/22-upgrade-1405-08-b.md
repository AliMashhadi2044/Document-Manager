## ۲. کار دستی یکم: مجوز تازهٔ `security_settings:write`

مهلت بی‌تحرکی نشست حالا از رابط تنظیم می‌شود و مجوز خودش را دارد. تا این مجوز
به نقش مدیر سامانه نرسد، زبانهٔ «امنیت نشست» دیده نمی‌شود (و مسیرش ۴۰۳ می‌دهد).

دو راه هست و **راه دوم برای نسخهٔ مستقر امن‌تر است**:

### راه الف — اجرای seed مرجع

```bash
npm run db:seed -w @dm/api        # یا در Docker: RUN_SEED=true
```

> ⚠️ **هشدار مهم.** این اسکریپت تخصیص مجوزهای نقش‌ها را با **ماتریس پیش‌فرض کد**
> هم‌راستا می‌کند: مجوزهایی که در ماتریس نیستند از نقش **حذف** می‌شوند. اگر در
> «مدیریت کاربران ← نقش‌ها و دسترسی‌ها» دسترسی نقشی را دست‌کاری کرده‌اید، آن
> تغییر برمی‌گردد به حالت پیش‌فرض. پیش از اجرا یک تصویر بگیرید:
>
> ```sql
> CREATE TABLE role_permissions_backup_1405_08b AS TABLE role_permissions;
> ```
>
> و برای دیدن اینکه چه چیزی حذف خواهد شد، فهرست فعلی را نگه دارید:
>
> ```sql
> SELECT r.key AS role, p.key AS permission
> FROM role_permissions rp
> JOIN roles r ON r.id = rp.role_id
> JOIN permissions p ON p.id = rp.permission_id
> ORDER BY r.key, p.key;
> ```

### راه ب — فقط همین مجوز (بدون دست زدن به بقیه)

هر دو دستور idempotent‌اند؛ اجرای دوباره‌شان بی‌اثر است.

```sql
INSERT INTO permissions (id, key, group_key, title_fa)
VALUES (gen_random_uuid(), 'security_settings:write', 'security_settings',
        'مدیریت تنظیمات امنیتی نشست')
ON CONFLICT (key) DO NOTHING;
```

```sql
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.key = 'SYSTEM_ADMIN' AND p.key = 'security_settings:write'
ON CONFLICT DO NOTHING;
```

بررسی:

```sql
SELECT p.key, r.key AS role
FROM permissions p
LEFT JOIN role_permissions rp ON rp.permission_id = p.id
LEFT JOIN roles r ON r.id = rp.role_id
WHERE p.key = 'security_settings:write';
```

باید یک ردیف با `SYSTEM_ADMIN` برگردد. (اگر نقش دیگری هم باید این اختیار را
داشته باشد، از همان صفحهٔ «نقش‌ها و دسترسی‌ها» بدهید؛ از SQL لازم نیست.)

### مهلت نشست پس از ارتقا

`SESSION_IDLE_TTL_MINUTES` در `.env` از این پس فقط **پیش‌فرض** است. تا کسی از
رابط عددی نگذارد، همان مقدار محیطی حاکم است — یعنی رفتار امروز عوض نمی‌شود.
بازهٔ مجاز ۵ تا ۷۲۰ دقیقه است و کادر خالی، مهلت را برنمی‌دارد (پیش‌فرض محیطی
برمی‌گردد). هر تغییر در ردپای حسابرسی با عنوان `SESSION_POLICY_SET` می‌نشیند.

## ۲.۵. دو مجوز تازهٔ فایل — همان کارِ بند ۲، برای دو مجوز دیگر

حذف پیوست تا امروز یک‌طرفه بود. حالا دو مسیر تازه دارد و هر کدام مجوز خودش را:

| مجوز | نقش پیش‌فرض | چه می‌کند |
|---|---|---|
| `attachment:restore` | بایگانی | فایل حذف‌شده را به سند برمی‌گرداند |
| `attachment:purge` | مدیر سامانه | فایل را برای همیشه پاک می‌کند، و صفحهٔ «پاک‌سازی فایل‌ها» را باز می‌کند |

این تقسیم همان مرزی است که برای سند کشیده شده: **حذف برگشت‌پذیر نزد کسی که کار
روزمره‌اش است، حذف دائمی نزد مدیر سامانه.** بایگانی که فایلی را اشتباهی برداشته،
خودش برمی‌گرداند؛ ولی پاک کردنِ همیشگی دست او نیست.

> **مدیر سامانه `attachment:read` نمی‌گیرد و این عمدی است.** او فهرست فایل‌های
> حذف‌شده را با نام، اندازه و ردپای حسابرسی می‌بیند و می‌تواند پاکشان کند — ولی
> محتوای هیچ فایلی را دانلود نمی‌کند. حق پاک کردن، حق دیدن نیست.

### راه الف — همان seed مرجع

```bash
npm run db:seed -w @dm/api
```

همان هشدار بند ۲ اینجا هم هست: seed تخصیص مجوز نقش‌ها را با فهرست مرجع
**هم‌راستا می‌کند**، یعنی اگر دستی مجوزی به نقشی داده‌اید که در فهرست نیست، برداشته
می‌شود.

### راه ب — فقط همین دو مجوز

```sql
INSERT INTO permissions (id, key, group_key, title_fa)
VALUES
  (gen_random_uuid(), 'attachment:restore', 'attachment', 'بازگرداندن فایل حذف‌شده'),
  (gen_random_uuid(), 'attachment:purge', 'attachment',
   'حذف دائمی فایل و پاک‌سازی فایل‌های بی‌سند')
ON CONFLICT (key) DO NOTHING;
```

```sql
-- بازگرداندن → بایگانی
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.key = 'ARCHIVIST' AND p.key = 'attachment:restore'
ON CONFLICT DO NOTHING;

-- حذف دائمی → مدیر سامانه
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
WHERE r.key = 'SYSTEM_ADMIN' AND p.key = 'attachment:purge'
ON CONFLICT DO NOTHING;
```

هر دو idempotent‌اند. تا این مجوزها نرسند، دکمه‌ها دیده نمی‌شوند و مسیرهایشان
۴۰۳ می‌دهند — یعنی رفتار امروز، بی‌هیچ تغییری.

## ۳. کار دستی دوم: قالب‌های گزارش

سه قالب سیستمی عوض شده‌اند:

| گزارش | تغییر |
|---|---|
| صورت ریز هزینه‌های **جاری** | ستون «تاریخ صورت حساب» (فقط روی صفحه، در چاپ/PDF/HTML نمی‌آید)؛ ستون «پرداخت ذی‌نفع» که شد «پرداخت به» با واژه: کارپرداز / ذی‌نفع / کارپرداز و ذی‌نفع / قبض؛ و **حذف ستون فصلِ صفر** (`faa0228`) |
| صورت ریز هزینه‌های **عمرانی** | ستون «تاریخ صورت حساب» (فقط روی صفحه)؛ و **حذف ستون فصلِ صفر** (`faa0228`) |
| لیست هزینهٔ سوخت | امضای «مسئول کارپردازی» به‌صورت پیش‌فرض |
| گزارش **مالیات** | شرطِ خاکستری شدن سلول «جمع کل» بالاتر از آستانه (`faa0228`)، و سرستونِ سه ستون دوبخشی که تکهٔ بی‌داده را می‌اندازد (`2d43220`) |

قالب سیستمی **داده** است، نه کد: تا seed اجرا نشود، این تغییرها در برنامه دیده
نمی‌شوند.

```bash
npm run db:seed -w @dm/api        # یا در Docker: RUN_SEED=true
```

نسخهٔ منتشرشدهٔ قبلی **ویرایش نمی‌شود**؛ نسخهٔ تازه‌ای منتشر می‌گردد و
خروجی‌های تاریخی به نسخهٔ خودشان بسته می‌مانند. پس گزارش‌هایی که قبلاً گرفته و
ذخیره شده‌اند عوض نمی‌شوند.

### ⚠️ تله: اگر قالب فعال، **کپیِ خودتان** باشد

seed فقط قالب **سیستمی** را به‌روز می‌کند. اگر از یک گزارش کپی گرفته‌اید و آن
کپی را قالب فعال کرده‌اید، seed به آن دست نمی‌زند و کاربر هیچ تغییری نمی‌بیند —
بدون هیچ خطایی. این را پیش از اجرا بسنجید:

```sql
SELECT t.key, d.name AS active_definition, d.is_system
FROM report_types t
LEFT JOIN report_definitions d ON d.id = t.active_definition_id
ORDER BY t.key;
```

هر ردیفی که `is_system = false` باشد، یعنی قالب فعالش کپیِ شماست. برای آن‌ها
تغییر را دستی ببرید:

۱. **طراح گزارش** → همان قالب فعال → **نسخهٔ پیش‌نویس تازه**
   (روی نسخهٔ منتشرشده دکمه‌اش «ویرایش بر پایه این نسخه» است).
۲. تغییرهای جدول بالا را روی آن اعمال کنید:
   - ستون تاریخ با `screenOnly`، ستون «پرداخت به» با مقدار `row.payeeTitle`،
     امضای `PROCUREMENT_LEAD`؛
   - برای فرم ریزهزینه: ستون **فصل** → **تنظیمات** → تیکِ «اگر در گزارش همه‌جا
     صفر بود، ستون حذف شود»؛
   - برای گزارش مالیات: ستون **جمع کل** → **تنظیمات** → «پس‌زمینهٔ خاکستری
     مشروط» (بند ۶).
۳. **انتشار**. تنظیم‌های خودتان (مثلاً تعداد ردیف خالی) دست‌نخورده می‌ماند.

> سرستونِ دوتکه‌ای گزارش مالیات (بند ۷) در طراح **ویرایش‌شدنی نیست** و فقط از
> قالب سیستمی می‌آید. اگر قالب مالیاتِ فعالتان کپیِ خودتان است، یا از قالب
> سیستمیِ تازه کپی تازه‌ای بگیرید، یا با همان سرستونِ ثابت بمانید — رفتار
> سلول‌ها (بند ۷، تکهٔ اول) در هر دو حالت درست است.

ساده‌ترین مرجع برای کپی کردن مقادیر، همان قالب سیستمیِ تازه‌منتشرشده است که در
کنار کپی شما در فهرست دیده می‌شود.

## ۴. تغییر رفتاری: روش پرداخت در فاکتور الزامی شد

«ثبت نشود» دیگر یک حالت نیست. از لحظهٔ استقرار:

- **فاکتور تازه** بدون روش پرداخت ثبت نمی‌شود (سرور ۴۲۲ می‌دهد: «روش پرداخت
  فاکتور الزامی است»). این سمت **سرور** بررسی می‌شود، نه فقط در فرم.
- **فاکتورهای قدیمیِ بدون روش پرداخت** سر جایشان می‌مانند و گزارش‌ها دست‌نخورده‌اند.
  باز کردنشان هم کار می‌کند؛ فیلد خالی نشان داده می‌شود. ولی **ویرایش و ثبت**
  آن فاکتور تا انتخاب روش پرداخت انجام نمی‌شود، و قاعدهٔ ثبت نهایی هم
  سرِ جایش است: سندِ دارای چنین فاکتوری با پیام «روش پرداخت انتخاب نشده است»
  ثبت نهایی نمی‌شود (این بررسی از قبل بود و عوض نشده).

پیش از استقرار بشمارید با چند مورد روبه‌رویید:

```sql
SELECT d.status, count(*) AS invoices
FROM invoices i
JOIN financial_documents d ON d.id = i.document_id
LEFT JOIN invoice_payments p ON p.invoice_id = i.id
WHERE p.invoice_id IS NULL
GROUP BY d.status
ORDER BY 2 DESC;
```

و برای دیدن اینکه کدام‌ها هستند (تا به کارپردازی بگویید):

```sql
SELECT d.id AS document_id, d.title, d.status, i.id AS invoice_id, i.description
FROM invoices i
JOIN financial_documents d ON d.id = i.document_id
LEFT JOIN invoice_payments p ON p.invoice_id = i.id
WHERE p.invoice_id IS NULL
ORDER BY d.created_at;
```

اگر همه در وضعیت `DRAFT` یا `REOPENED` باشند (در محیط توسعه همین‌طور بود:
۱۱ پیش‌نویس و ۱ بازگشایی‌شده)، کار خاصی لازم نیست: هیچ سند ثبت‌شده‌ای
تحت‌تأثیر نیست و اصلاحشان با یک‌بار ویرایش انجام می‌شود. **هیچ اسکریپتِ پر کردن
خودکار ندهید**: روش پرداخت یک واقعیت مالی است و حدس زدنش یعنی نوشتن داده‌ای که
کسی تأیید نکرده.

## ۵. بقیهٔ تغییرهای رفتاری — بی‌نیاز از کار دستی

۱. **کد ملی با صفر ابتدایی، درست نمایش داده می‌شود.** پیش از این موتور گزارش
   رشتهٔ تمام‌رقمی را عدد می‌خواند و `0123456789` به `123456789` تبدیل می‌شد.
   داده در پایگاه داده همیشه درست بود؛ فقط نمایش خراب بود. گزارش‌هایی که
   قبلاً به‌صورت فایل گرفته شده‌اند عوض نمی‌شوند — در صورت نیاز دوباره بگیرید.

۲. **ردپای حسابرسی برای دو عمل، از این پس ثبت می‌شود.** `entity_id` ستونی از
   نوع UUID است و کلیدِ رشته‌ایِ تنظیم به آن می‌رفت؛ خطا بیرون از تراکنش فقط
   لاگ می‌شد و درخواست ۲۰۰ برمی‌گرداند. نتیجه این بود که `BASE_DATA_REORDER` در
   کل تاریخ پایگاه داده **صفر** ردیف داشت و تغییر پیش‌فرض مالیات سازمان هیچ
   ردی نمی‌گذاشت. حالا کلید در `entity_type` می‌نشیند. رخدادهای گذشته
   بازسازی‌شدنی نیستند.

۳. **صفحهٔ فصل‌ها دیگر با پاسخِ بدون «پیش‌فرض‌های فاکتور» از کار نمی‌افتد.** این
   حالت وقتی پیش می‌آمد که رابطِ تازه به سرویسِ قدیمی وصل می‌شد — یعنی دقیقاً
   در فاصلهٔ بین به‌روزرسانی دو سرویس. فقط اصلاح رابط است.

۴. **Tab از فهرست انتخابِ بازشده، داخل همان فرم می‌ماند.** مربوط به ترجیح
   «ظاهر و شخصی‌سازی ← فهرست‌های انتخاب با Tab ← با رسیدن فوکوس باز شود» است:
   پیش از این Tab کاربر را از فرم بیرون می‌انداخت و فوکوس سر از منوی کنار صفحه
   درمی‌آورد. ترجیح کاربران دست‌نخورده می‌ماند.

## ۶. تنظیم تازه: آستانهٔ علامت‌گذاری مبلغ در گزارش مالیات

ردیفی که جمع کلش از یک مبلغ بیشتر باشد، سلول مبلغش در گزارش مالیات **پس‌زمینهٔ
خاکستری** می‌گیرد — در HTML، PDF و Excel. رنگ **متن** دست نمی‌خورد: علامت باید
دیده شود، ولی عددی که علامت خورده همان عددی است که باید خوانده شود.

خودِ آستانه یک تنظیم سازمانی است و نه عددی داخل قالب، چون سالی یک بار عوض
می‌شود و نباید هر بار انتشار نسخهٔ تازهٔ قالب بخواهد.

**پس از ارتقا هیچ کاری لازم نیست.** تنظیم تازه خودبه‌خود **خاموش** است:

- کلیدش `report_settings` در جدول `system_settings` است و تا اولین ذخیره اصلاً
  ساخته نمی‌شود. `system_settings` یک جدول کلید/مقدار است، پس این **مهاجرت
  نیست** و ستونی اضافه نمی‌شود.
- مقدار خالی یعنی خاموش: هیچ سلولی علامت نمی‌خورد و گزارش دقیقاً مثل قبل است.

برای روشن کردنش: **اطلاعات پایه ← فصل‌ها و انواع فاکتور ← علامت‌گذاری مبلغ در
گزارش مالیات**، عدد را به ریال بنویسید و ذخیره کنید. مقایسه «بیشتر از» است، پس
مبلغِ **برابر** با آستانه علامت نمی‌خورد.

مجوزش `financial_settings:write` است — **همان مجوز پیش‌فرض‌های مالیات که از
قبل وجود دارد**. هیچ مجوز تازه‌ای در این نسخه اضافه نشده، پس بند ۲ برای این
تنظیم تکرار نمی‌شود.

برای دیدن مقدار فعلی:

```sql
SELECT value FROM system_settings WHERE key = 'report_settings';
```

نبودنِ ردیف یعنی خاموش.

## ۷. تغییرهای دیدنیِ گزارش‌ها — بی‌نیاز از کار دستی

تکه‌های ۱ و ۳ علاوه بر کد، به اجرای seed قالب‌ها (بند ۳) هم نیاز دارند؛
بقیه فقط با استقرار کد اعمال می‌شوند.

۱. **ستون فصلی که در یک سند هیچ خرجی ندارد، در فرم ریزهزینه چاپ نمی‌شود.**
   سازمانی که ده فصل تعریف کرده، تا امروز روی هر فرم ده ستون می‌گرفت — حتی اگر
   آن سند فقط در دو فصل خرج داشته باشد. تصمیم **به ازای هر اجرا** گرفته می‌شود
   و نه یک بار در قالب. دو حالت دست نگه می‌دارد: جدولِ بی‌ردیف (فرم خالی برای
   پر کردن با دست) ستون‌هایش را کامل نگه می‌دارد، و حذف هیچ‌وقت جدول را
   بی‌ستون نمی‌کند. ردیف جمع و ادغام خانه‌ها با ستون‌های **مانده** حساب
   می‌شوند. خاموش کردنش یک تیک است: ستون فصل → تنظیمات.

۲. **سلول دوبخشی وقتی یک نیمه‌اش نیست، یک‌تکه می‌شود.** در گزارش مالیات،
   فروشنده‌ای که چند فاکتور دارد طبق قاعدهٔ تجمیع شمارهٔ صورت‌حساب نمی‌گیرد؛ تا
   امروز سلولش نیمهٔ بالای خالی داشت، یک خط افقیِ بی‌دلیل وسطش، و تاریخ در
   نیمهٔ پایین. حالا همان سلول یک‌تکه است و فقط تاریخ را نشان می‌دهد.

   همین برای «نام — کد ملی» هم هست: فروشنده‌ای که نه کد ملی دارد و نه شمارهٔ
   اقتصادی، سلولش فقط نام را نشان می‌دهد.

   **ولی «تلفن — کد پستی» فرق دارد و عمداً عوض نشده**: قالب برای تلفنِ نبوده
   «—» چاپ می‌کند، و «—» یک متن است و نه جای خالی. پس فروشنده‌ای که تلفن ندارد
   ولی کد پستی دارد، همچنان سلولی دوتکه با «—» در بالا می‌گیرد. اگر این را هم
   می‌خواهید یک‌تکه شود، در طراح گزارش `emptyText` آن ستون را خالی کنید — ولی
   آن‌وقت فروشنده‌ای که هیچ‌کدام را ندارد، سلولِ کاملاً خالی می‌گیرد به‌جای
   «—».

۳. **سرستون، تکه‌ای را که در هیچ ردیفی داده ندارد می‌اندازد.** گزارشی که هیچ
   ردیفش شمارهٔ صورت‌حساب ندارد، سرستونش «تاریخ صورت حساب» می‌شود و نه «شماره
   صورت حساب — تاریخ صورت حساب». اگر حتی **یک** ردیف شماره داشته باشد، سرستون
   کامل می‌ماند: سرستون دربارهٔ ستون است و نه یک ردیف. وقتی هیچ تکه‌ای داده
   ندارد، عنوان ثابتِ ستون می‌ماند.

۴. **ستون‌های درهم‌رفتهٔ جدول در چاپ، رفع شد.** یک اشتباه در تولید HTML باعث
   می‌شد هر سلولِ ردیفِ داده از سومی به بعد `colspan` بگیرد — سلول سوم
   `colspan="2"`، چهارمی `colspan="3"` و همین‌طور تا آخر. جدول دوازده‌ستونیِ
   گزارش مالیات روی کاغذ ده‌ها ستون می‌شد و خانه‌هایش روی هم می‌افتادند. این
   روی **همهٔ** گزارش‌ها اثر داشت و فقط در خروجی چاپی/PDF دیده می‌شد. هیچ
   داده‌ای درگیر نبود و هیچ کار دستی ندارد؛ خروجی‌های قبلیِ ذخیره‌شده عوض
   نمی‌شوند و در صورت نیاز باید دوباره گرفته شوند.

۵. **ویرایش شمارهٔ گردش و تاریخ گردش سند، حالا واقعاً ذخیره می‌شود.** پیش از
   این فرم پیام «مشخصات سند اصلاح شد» می‌داد و هیچ‌چیز عوض نمی‌شد: دو کلید در
   schema سمت سرور تعریف نشده بودند و خاموشانه دور انداخته می‌شدند. داده‌ای از
   دست نرفته بود — آن ویرایش‌ها اصلاً انجام نشده بودند. **اسنادی را که فکر
   می‌کردید شمارهٔ گردششان را اصلاح کرده‌اید، دوباره بررسی کنید.**

   ```sql
   SELECT id, title, workflow_number, workflow_date
   FROM financial_documents
   WHERE deleted_at IS NULL AND workflow_number IS NULL
   ORDER BY created_at DESC LIMIT 50;
   ```

۶. **پلاک خودرو با قالب خوانا نشان داده می‌شود** (`c06569e`) — فقط نمایش در
   فهرست انتخاب خودرو؛ داده دست‌نخورده است.

## ۸.۵. طراح گزارش: تنظیم‌هایی که حالا کار می‌کنند، و روندی که کوتاه شد

### تنظیم‌هایی که تا امروز بی‌اثر بودند

هر پنج مورد یک شکل داشتند: کنترل در فرم هست، مقدارش ذخیره می‌شود، و رندر
هیچ‌وقت نمی‌خواندش. **هیچ کار دستی ندارند** — با استقرار کد درست می‌شوند.

| تنظیم | تا امروز | از این پس |
|---|---|---|
| اندازهٔ کاغذ | در HTML اثر داشت، در PDF همیشه A4 | PDF هم از قالب می‌خواند |
| پس‌زمینهٔ سلول | در PDF حذف می‌شد | در PDF هم چاپ می‌شود |
| بلوک «شماره صفحه» | عیناً `{{page}}` روی کاغذ می‌آمد | به پابرگِ چاپ می‌رود، با شمارهٔ واقعی |
| تکرار سربرگ/پابرگ | بی‌اثر | روی هر صفحهٔ چاپ تکرار می‌شود |
| تکرار سرستون جدول | همیشه روشن | تیکش واقعاً اثر دارد |

و کنترلِ «اندازهٔ قلم عنوان» (`headingFontSizePt`) **حذف شد**: این موتور بلوکی
به نام «عنوان» ندارد و آن عدد هیچ‌جا خوانده نمی‌شد. عنوان گزارش یک بلوک متنی
است و اندازهٔ قلم خودش را دارد. قالب‌های ذخیره‌شده مشکلی ندارند.

> نکتهٔ مهم برای بند ۶: علامت‌گذاری خاکستری **حالا در PDF هم دیده می‌شود**.
> پیش از این فقط در HTML و Excel بود.

### روند ویرایش قالب

برای عوض کردن یک حاشیه روی یک گزارش سیستمی، پنج گام در دو صفحه لازم بود:
کپی ← فعال‌سازی ← ویرایش ← ذخیره پیش‌نویس ← انتشار نسخه. حالا دو گام است:
**ویرایش ← انتشار و اعمال**.

- **«ویرایش»** روی هر ردیفِ فهرست قالب‌ها: اگر قالب سیستمی باشد، سرور خودش یک
  «نسخهٔ سازمانی» می‌سازد و کاربر مستقیم در طراح می‌نشیند. زدن دوباره‌اش کپی
  تکراری نمی‌سازد. «کپی تازه» هنوز هست، برای وقتی واقعاً چند قالب می‌خواهید.
- **«انتشار و اعمال»** جای «انتشار نسخه» + «فعال‌سازی قالب» را گرفت.
- **نوار هشدار** بالای طراح می‌گوید چرا آنچه می‌بینید هنوز در خروجی‌ها نیست
  (تغییر ذخیره‌نشده / نسخهٔ پیش‌نویس / قالبِ غیرفعال).
- **رفتن به تب پیش‌نمایش** اول پیش‌نویس را ذخیره می‌کند، تا پیش‌نمایشِ کهنه
  نبینید.

قاعده‌های محافظ دست‌نخورده‌اند: نسخهٔ منتشرشده همچنان تغییرناپذیر است و قالب
سیستمی همچنان ویرایش نمی‌شود. فقط اجرایشان از دوش کاربر برداشته شد.

**کار دستی ندارد.** ولی اگر در نسخهٔ مستقر قالبِ فعالِ یک گزارش کپیِ خودتان است
(بند ۳)، حالا «ویرایش» روی ردیفِ سیستمی همان کپیِ فعال را باز می‌کند — یعنی
همان چیزی که واقعاً خروجی را می‌سازد.

## ۸.۶. پیوست حذف‌شده: برگشت، پاک شدن، و فایل‌هایی که جا مانده‌اند

### آنچه تا امروز بود

حذف پیوست، `deleted_at` را پر می‌کرد و فایل از هر نمایی بیرون می‌رفت. از آنجا به
بعد هیچ: نه بازگشتی، نه پاک شدنی. و کامنت بالای همان تابع می‌گفت شیء ذخیره‌سازی
«طبق سیاست retention بعداً پاک می‌شود» — **چنین سیاستی وجود نداشت.** سرویس
نگهداشت فقط اعلان‌های خوانده‌شده و رویدادهای امنیتی را جارو می‌کند. هر فایلی که
تا امروز حذف شده، هنوز بایت‌به‌بایت در ذخیره‌سازی شماست.

این خبر خوبی است: یعنی **هر فایلی که اشتباهی حذف شده، همین حالا قابل برگرداندن
است.** پس از استقرار، از برگهٔ همان سند «فایل‌های حذف‌شدهٔ این سند» را باز کنید.

### بازگرداندن

بخشی تاشو زیر پنل پیوست‌های هر سند. سه چیز جلوی بازگرداندن را می‌گیرند و هر سه
پیام روشن می‌دهند: سقف تعداد یا حجم سند پر شده باشد، همان محتوا در این فاصله
دوباره آپلود شده باشد، یا بایگانی سند نهایی شده باشد. و اگر شیء فایل در
ذخیره‌سازی نباشد، برنمی‌گردد — ردیفی که فایلش نیست، «برگشتن»ش دروغ است.

### حذف دائمی

فقط روی فایلی که **از قبل حذف شده**. دو مرحله‌ای بودنش عمدی است: کسی که فایل را
برمی‌دارد و کسی که پاکش می‌کند، در نقش‌های پیش‌فرض یکی نیستند.

پیش از پاک شدن، یک ردیف حسابرسی با نام، اندازه، checksum، کلید شیء، و اینکه چه
کسی آپلود و چه کسی حذف کرده بود نوشته می‌شود. پس از آن، تنها چیزی که از فایل
می‌ماند همین است.

رابط، عبارت «حذف دائمی» را تایپی می‌خواهد — همان قاعدهٔ حذف دائمی سند.

### صفحهٔ تازه: «پاک‌سازی فایل‌ها» (سامانه ← پاک‌سازی فایل‌ها)

ذخیره‌سازی و پایگاه داده همیشه دقیقاً یکی نمی‌مانند. این صفحه دو چیز را نشان
می‌دهد:

- **فایل‌های بی‌صاحب**: شیءهایی که هیچ ردیف پیوستی سراغشان را نمی‌گیرد — ته‌ماندهٔ
  آپلودهای قطع‌شده، اسناد حذف‌دائمی‌شده، یا بازگرداندن پشتیبان پایگاه داده.
- **ردیف‌های آپلود نیمه‌کاره**: ردیف‌هایی که در وضعیت `PENDING` مانده‌اند و هیچ
  فایلی ندارند.

سه چیز را بدانید:

1. **پیمایش با دکمه شروع می‌شود**، نه با باز شدن صفحه: هر پیمایش، فهرست کردن کل
   bucket است.
2. **دورهٔ امان ۲۴ ساعته.** شیئی که همین حالا آپلود می‌شود، برای لحظه‌ای دقیقاً
   شکل یک یتیم دارد (ترتیب آپلود «ردیف ← شیء ← به‌روزرسانی ردیف» است). بی این
   دوره، پاک‌سازی آپلودِ در جریانِ یک کاربر دیگر را از زیر دستش می‌برد.
3. **فایلِ حذف‌شده اینجا نمی‌آید.** او هنوز صاحب دارد و باید بازگشتنی بماند.

پیش از اولین پاک‌سازی روی نسخهٔ مستقر، **از bucket پشتیبان بگیرید**: این صفحه
نسخهٔ پشتیبان نمی‌سازد و آنچه پاک می‌شود برنمی‌گردد.

**کار دستی ندارد** (جز مجوزهای بند ۲.۵).

## ۹. ترتیب اجرا

```bash
# ۱. پشتیبان تازه — پیش از هر چیز
npm run backup

# ۲. وضعیت فعلی را بسنجید (بندهای ۳ و ۴ همین سند)
#    کدام قالب فعال، کپیِ کاربر است؟ چند فاکتور بدون روش پرداخت است؟

# ۳. تصویر نسخهٔ تازه
docker build -t document-manager:1405-08b .

# ۴. توقف سرویس
docker compose stop api

# ۵. مهاجرت — در این نسخه چیزی برای اجرا ندارد، ولی بی‌خطر و لازم است
npx prisma migrate deploy --schema apps/api/prisma/schema.prisma

# ۶. داده مرجع: مجوزهای تازه (بندهای ۲ و ۲.۵) + نسخهٔ تازهٔ قالب‌های گزارش
#    هشدار بند ۲ را خوانده باشید (تخصیص مجوز نقش‌ها هم‌راستا می‌شود).
npm run db:seed -w @dm/api        # یا RUN_SEED=true در Docker

# ۷. بالا آوردن
docker compose up -d api

# ۸. سلامت
curl -fsS http://localhost:3100/api/v1/health

# ۹. یک گزارش واقعی بگیرید و چاپش را ببینید
#    ستون‌های جدول باید منظم باشند (بند ۷، تکهٔ چهارم).
```

اگر نمی‌خواهید seed تخصیص نقش‌ها را دست بزند: مرحلهٔ ۶ را با **راه ب** بندهای ۲
و ۲.۵ جایگزین کنید — ولی توجه کنید که قالب‌های گزارش بند ۳ هم از همین seed می‌آیند.
در این صورت قالب‌ها را دستی از طراح گزارش به‌روز کنید.

### برگشت (rollback)

شِما عوض نشده، پس نسخهٔ قبلی کد با همین پایگاه داده **کار می‌کند**. دو نکته:

- مجوز تازه در پایگاه داده می‌ماند و بی‌اثر است؛ کد قدیمی سراغش نمی‌رود. همین
  برای `attachment:restore` و `attachment:purge` هم صادق است.
- **فایلی که با نسخهٔ تازه برای همیشه پاک شده، با برگشت برنمی‌گردد.** این تنها
  تغییرِ این نسخه است که برگشت‌ناپذیر است؛ اگر هنوز تصمیم نگرفته‌اید، تا مطمئن
  شدن هیچ فایلی را «حذف دائمی» نکنید. فایل‌های صرفاً **حذف‌شده** دست‌نخورده‌اند و
  کد قدیمی هم مثل همیشه نشانشان نمی‌دهد.
- نسخهٔ تازهٔ قالب‌های گزارش هم می‌ماند و کد قدیمی هم همان را اجرا می‌کند. اگر
  می‌خواهید گزارش به شکل قبلی برگردد، از طراح گزارش نسخهٔ قبلی را فعال کنید
  (نسخه‌های قدیمی حذف نشده‌اند).
- تنظیم `session_policy` در `system_settings` می‌ماند؛ کد قدیمی آن را نمی‌خواند
  و به `SESSION_IDLE_TTL_MINUTES` برمی‌گردد.
- تنظیم `report_settings` هم می‌ماند و بی‌اثر است؛ کد قدیمی سراغش نمی‌رود و
  گزارش مالیات بدون علامت خاکستری چاپ می‌شود.
- قالب‌های تازه را کد قدیمی **می‌خواند ولی نمی‌فهمد**: `dropWhenAllZero`،
  `shadeWhen` و `titleParts` کلیدهایی‌اند که موتور قدیمی نمی‌شناسد و کنار
  می‌گذارد. گزارش اجرا می‌شود، فقط این سه رفتار را ندارد. اگر دقیقاً شکل قبلی
  را می‌خواهید، از طراح گزارش نسخهٔ قبلی قالب را فعال کنید.
- ستون‌های درهم‌رفتهٔ چاپ (بند ۷، تکهٔ چهارم) با برگشت **برمی‌گردند**.

نیازی به برگرداندن پایگاه داده نیست.
