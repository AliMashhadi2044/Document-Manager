
# ADR-0001 — Monorepo با npm workspaces

**وضعیت:** پذیرفته · **تاریخ:** فاز ۰

## زمینه

پروژه دو برنامه (web و api) و چند پکیج مشترک دارد. پکیج `shared` **باید** بین کلاینت و
سرور مشترک باشد، چون تنها راه جلوگیری از واگرایی محاسبات مالی و schemaهای اعتبارسنجی
همین است (ریسک R1). محیط توسعه: Node 24.12 و npm 11.6 نصب‌اند؛ pnpm نصب نیست.

## تصمیم

Monorepo با **npm workspaces**. بدون pnpm، بدون Nx، بدون Turborepo.
ترتیب build به‌صورت صریح در scriptهای ریشه مدیریت می‌شود:
`shared` → `report-engine` → `api` و `web`.

## دلایل

- npm 11 از قبل در محیط هست؛ افزودن package manager دوم یک گام نصب و یک منبع خطا
  برای هر توسعه‌دهنده جدید اضافه می‌کند.
- تعداد پکیج‌ها کم است (۲ app + ۳ package). مزیت اصلی Nx/Turbo (کش build گراف‌محور)
  در این اندازه محسوس نیست، ولی هزینه پیکربندی و نگهداری‌اش محسوس است.
- ساختار workspace استاندارد است؛ اگر بعداً لازم شد، مهاجرت به pnpm یا Turborepo
  **بدون تغییر ساختار پوشه‌ها** انجام می‌شود.

## جایگزین‌های رد‌شده

| جایگزین | دلیل رد |
|---|---|
| pnpm workspaces | نیاز به نصب و آموزش ابزار جدید؛ مزیت فضای دیسک برای این اندازه حاشیه‌ای است |
| Nx یا Turborepo | پیچیدگی پیکربندی بیشتر از ارزش آن در این مقیاس |
| چند مخزن جدا | `packages/shared` را عملاً غیرممکن یا دردناک می‌کند و ریسک R1 را فعال می‌کند |
| کپی کد مشترک در دو پروژه | ناسازگاری محاسبات مالی — خطرناک‌ترین گزینه |

## پیامدها

- برای افزودن وابستگی به یک workspace باید `-w <name>` استفاده شود.
- بدون کش build توزیع‌شده؛ در CI زمان build کل مخزن پرداخت می‌شود (در این اندازه قابل قبول).

## معیار بازنگری

اگر تعداد workspaceها از ۸ بگذرد، یا زمان CI از ۱۰ دقیقه عبور کند، یا پکیج چهارمی
با build سنگین اضافه شود → Turborepo بازبینی می‌شود.
