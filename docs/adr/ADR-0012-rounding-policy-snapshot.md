
# ADR-0012 — snapshot سیاست گرد کردن روی سند

**وضعیت:** پذیرفته · **تاریخ:** پس از پاسخ Q3

## زمینه

کارفرما تصمیم گرفت سیاست گرد کردن **در تنظیمات قابل تغییر** باشد (پاسخ Q3): هم محل
گرد کردن (سطح ردیف یا سطح فاکتور) و هم جهت آن (half-up، floor، half-even).

این انعطاف یک خطر جدی ایجاد می‌کند که در طراحی اولیه وجود نداشت:
اگر محاسبه همیشه سیاست **فعلی** را بخواند، تغییر تنظیمات در آینده باعث می‌شود بازمحاسبه
اسناد گذشته عدد **متفاوتی** بدهد. آن‌وقت:

- تطبیق مالی (جمع ردیف = جمع فاکتور = جمع سند) روی اسناد قدیمی می‌شکند،
- ثبت نهایی مجدد یک سند بازگشایی‌شده مبالغ را بی‌صدا تغییر می‌دهد،
- بازتولید یک گزارش تاریخی با خروجی چاپ‌شده قبلی نمی‌خواند.

این ریسک R14 است و احتمالش بالاست، چون دقیقاً همان کاری است که یک تنظیم قابل تغییر
دعوت به انجامش می‌کند.

## تصمیم

سیاست گرد کردن **داده سند** است، نه تنظیم سراسری زنده.

```
system_settings.rounding_policy          ← پیش‌فرض سازمان (قابل تغییر)
        │  در لحظه ایجاد سند کپی می‌شود
        ▼
financial_documents.rounding_policy      ← snapshot، مرجع محاسبه همان سند
```

قواعد:

1. سند در لحظه **ایجاد**، سیاست فعلی سازمان را کپی می‌کند.
2. تا وقتی سند `DRAFT` است، کاربر دارای `financial_settings:write` می‌تواند آن را به
   سیاست فعلی سازمان **هم‌راستا کند** (اقدام صریح، نه خودکار).
3. با **ثبت نهایی**، سیاست سند **قفل** می‌شود و دیگر تغییر نمی‌کند — حتی در بازگشایی.
4. همه محاسبات آن سند، در هر لایه (کلاینت، سرور، موتور گزارش)، سیاست را از **خود سند**
   می‌خوانند، نه از تنظیمات سراسری.
5. سیاست در `document_revisions.snapshot` هم ثبت می‌شود تا بازتولید خروجی تاریخی دقیق بماند.

```ts
export interface RoundingPolicy {
  scope: 'LINE' | 'INVOICE';              // محل گرد کردن
  mode: 'HALF_UP' | 'FLOOR' | 'HALF_EVEN'; // جهت گرد کردن
}
// پیش‌فرض سازمان: { scope: 'LINE', mode: 'HALF_UP' }
```

## دلایل

- **تغییرناپذیری مبالغ تاریخی.** سندی که ثبت شده، عددش دیگر عوض نمی‌شود. این برای یک
  سامانه مالی غیرقابل مذاکره است.
- **بازتولیدپذیری.** گزارش تاریخی به `document_revision` بسته است و حالا سیاست محاسبه هم
  داخل همان snapshot است؛ پس بازتولید واقعاً بیت‌به‌بیت است.
- **انعطاف واقعی بدون خطر.** سازمان می‌تواند سیاست را عوض کند؛ اثرش فقط روی **اسناد
  جدید** است — که همان چیزی است که کاربر از «تغییر تنظیمات» انتظار دارد.
- **تشخیص‌پذیری.** چون سیاست روی سند ذخیره است، در صفحه جزئیات و در «جزئیات مبالغ»
  قابل نمایش است: کاربر می‌بیند این سند با چه قاعده‌ای محاسبه شده.

## جایگزین‌های رد‌شده

| جایگزین | دلیل رد |
|---|---|
| خواندن سیاست سراسری در زمان محاسبه | تغییر تنظیمات، مبالغ اسناد گذشته را عوض می‌کند — ریسک R14 |
| سیاست ثابت در کد (بدون تنظیم) | خلاف تصمیم صریح کارفرما در پاسخ Q3 |
| سیاست تاریخ‌دار سراسری (effective_from) | بهتر از سراسری زنده، ولی سند بازگشایی‌شده هنوز ممکن است به بازه دیگری بیفتد؛ snapshot روی سند صریح‌تر و ساده‌تر است |
| snapshot روی هر فاکتور | سند واحد ثبت نهایی است؛ سیاست متفاوت بین فاکتورهای یک سند بی‌معنا و گیج‌کننده است |

## پیامدها

- ستون `rounding_policy jsonb NOT NULL` روی `financial_documents`.
- امضای توابع مالی سیاست را **صریح** می‌گیرند؛ هیچ تابعی سیاست را از متغیر سراسری
  نمی‌خواند:
  ```ts
  calculateLine(input: LineInput, policy: RoundingPolicy): LineResult
  ```
  این باعث می‌شود فراموش کردن سیاست یک **خطای کامپایل** باشد، نه یک باگ خاموش.
- `divRoundHalfUp` به یک تابع عمومی‌تر `roundDiv(numerator, denominator, mode)` تبدیل
  می‌شود؛ همچنان **تنها** تابع گرد کردن پروژه.
- در حالت `scope: 'INVOICE'`، مالیات یک‌بار روی جمع خالص فاکتور محاسبه می‌شود و
  مالیات ردیف‌ها به‌صورت **سهم تخصیصی** نمایش داده می‌شود؛ تخصیص باید جمع‌شونده باشد
  (باقیمانده به بزرگ‌ترین ردیف داده می‌شود) تا جمع ستون با جمع فاکتور بخواند.
- تست‌های اجباری: هر سه `mode` × هر دو `scope` · تغییر تنظیمات سازمان پس از ثبت سند ←
  مبالغ سند **بدون تغییر** · بازگشایی و ثبت مجدد ← همان سیاست قبلی اعمال شود.
