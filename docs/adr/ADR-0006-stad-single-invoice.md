
# ADR-0006 — محدودیت فاکتور ستاد با ایندکس یکتای جزئی و FK ترکیبی

**وضعیت:** پذیرفته · **تاریخ:** فاز ۰

## زمینه

سند «سامانه ستاد» حداکثر یک فاکتور دارد. پرامپت صریحاً می‌خواهد این محدودیت در Frontend،
Backend **و دیتابیس** اعمال شود تا درخواست‌های همزمان هم نتوانند فاکتور دوم بسازند
(ریسک R7). مشکل فنی: نوع سند روی `financial_documents` است، نه روی `invoices` — پس
نمی‌شود مستقیم ایندکس جزئی شرطی روی `invoices` ساخت.

## تصمیم

```sql
ALTER TABLE financial_documents
  ADD CONSTRAINT financial_documents_id_type_uk UNIQUE (id, type);

ALTER TABLE invoices ADD COLUMN document_type document_type NOT NULL;

ALTER TABLE invoices ADD CONSTRAINT invoices_document_fk
  FOREIGN KEY (document_id, document_type)
  REFERENCES financial_documents (id, type)
  ON UPDATE CASCADE;

CREATE UNIQUE INDEX invoices_one_per_stad_document_uk
  ON invoices (document_id) WHERE document_type = 'STAD';
```

## دلایل

این ترکیب سه تضمین می‌دهد که هیچ‌کدام به کد وابسته نیست:

1. **ضد همزمانی.** ایندکس یکتا در سطح موتور دیتابیس اجرا می‌شود؛ دو تراکنش موازی
   نمی‌توانند هر دو موفق شوند، بدون نیاز به `SERIALIZABLE` یا قفل مشورتی.
2. **ضد ناسازگاری denormal.** `document_type` روی فاکتور یک کپی است و کپی‌ها از هم
   می‌پاشند — مگر با FK ترکیبی به `(id, type)` که آن را به مقدار واقعی سند **گره** می‌زند.
3. **رفتار درست تغییر نوع سند.** تغییر «عادی ← ستاد» روی سندی که دو فاکتور دارد، با
   `ON UPDATE CASCADE` منتشر می‌شود، ایندکس یکتا نقض می‌شود و تراکنش **رد** می‌شود.
   یعنی همان رفتار مطلوب، بدون نوشتن کد نگهبان جداگانه.

## جایگزین‌های رد‌شده

| جایگزین | دلیل رد |
|---|---|
| بررسی `count()` در کد سرویس | شرط مسابقه‌ای: دو درخواست موازی هر دو صفر می‌بینند |
| تراکنش `SERIALIZABLE` | هزینه و خطای serialization در کل مسیر، برای یک قاعده موضعی |
| قفل مشورتی (`pg_advisory_lock`) | کار می‌کند ولی نامرئی و فراموش‌شدنی است؛ constraint خوداظهار است |
| تریگر دیتابیس | منطق پنهان، سخت‌تر برای تست و بازبینی نسبت به یک ایندکس اعلانی |
| ستون `invoice_id` روی سند (رابطه ۱:۱) | مدل را برای سند عادی که چند فاکتور دارد خراب می‌کند |

## پیامدها

- `invoices.document_type` یک ستون denormal است که **فقط** با FK نگهداری می‌شود؛ کد
  هرگز آن را مستقل تغییر نمی‌دهد (مقدار در زمان insert از سند خوانده می‌شود).
- Prisma این constraintها را به‌تنهایی تولید نمی‌کند → در migration با SQL خام
  نوشته و در بازبینی علامت‌دار می‌شوند.
- خطای یکتایی دیتابیس باید به پیام فارسی قابل فهم ترجمه شود:
  «سند سامانه ستاد فقط می‌تواند یک فاکتور داشته باشد.»
- تست اجباری: دو درخواست **موازی** ایجاد فاکتور → دقیقاً یکی موفق.
