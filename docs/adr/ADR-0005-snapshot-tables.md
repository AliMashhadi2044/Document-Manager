
# ADR-0005 — snapshot در جدول ساختارمند، نه JSON

**وضعیت:** پذیرفته · **تاریخ:** فاز ۰

## زمینه

تغییر اطلاعات پایه (نام یا آدرس فروشنده، عنوان فصل، نام مدرسه) **نباید** اسناد ثبت‌شده و
خروجی‌های تاریخی را تغییر دهد (ریسک R6). همزمان، گزارش مالیات باید روی همین اطلاعات
تاریخی **تجمیع، فیلتر و مرتب‌سازی** کند.

## تصمیم

- `vendor_snapshots` و `buyer_snapshots` جداول **تغییرناپذیر** با ستون‌های تایپ‌شده.
- هر فاکتور **ردیف snapshot اختصاصی خودش** را دارد (به اشتراک گذاشته نمی‌شود).
- مقادیر کوچک‌تر (عنوان فصل، نام مدرسه، ناحیه، نوع انشعاب، پلاک، شبا، نام بانک) به‌صورت
  ستون `*_snapshot` کنار FK زنده روی همان جدول ذخیره می‌شوند.
- FK به رکورد زنده **حفظ** می‌شود (nullable) برای گزارش‌گیری و پیشنهاد نوع کالا.

## دلایل

- **کوئری‌پذیری.** گزارش مالیات بر اساس هویت تاریخی فروشنده گروه‌بندی و مرتب می‌شود.
  با JSON بی‌schema این کوئری‌ها شکننده، غیرقابل ایندکس و کند می‌شوند.
- **صحت.** ستون تایپ‌شده می‌تواند `NOT NULL` و `CHECK` داشته باشد؛ کلید JSON نه.
- **ردیف اختصاصی.** اگر snapshot بین فاکتورها مشترک باشد، یک `UPDATE` اشتباه چندین
  سند تاریخی را خراب می‌کند. ردیف اختصاصی این مسیر را می‌بندد.
- تغییرناپذیری با `REVOKE UPDATE` روی این جداول از نقش برنامه قابل تثبیت است.

## جایگزین‌های رد‌شده

| جایگزین | دلیل رد |
|---|---|
| `snapshot jsonb` روی فاکتور | غیرقابل ایندکس و تجمیع؛ بدون اعتبارسنجی نوع |
| فقط FK به رکورد زنده | تغییر اطلاعات پایه، اسناد گذشته را عوض می‌کند — نقض الزام صریح |
| نسخه‌بندی خود جدول فروشنده (SCD-2) | پیچیدگی بالا در هر کوئری؛ snapshot ساده‌تر و صریح‌تر است |
| snapshot مشترک با content-hash | صرفه‌جویی فضا در برابر ریسک خرابی چندسندی — معامله بدی است |

## پیامدها

- حجم داده بیشتر (تکرار اطلاعات فروشنده در هر فاکتور). برای این مقیاس بی‌اهمیت است.
- ایجاد فاکتور باید **همیشه** snapshot بسازد؛ این در اعتبارسنجی ثبت نهایی بررسی می‌شود.
- تنها استثنای JSON در پروژه `document_revisions.snapshot` است، چون هدفش بازسازی
  وضعیت است نه کوئری ([ADR-0009](ADR-0009-document-revisions.md)).
- تست یکپارچه اجباری: تغییر فروشنده پس از ثبت → سند، فاکتور و گزارش قبلی **بی‌تغییر**.
