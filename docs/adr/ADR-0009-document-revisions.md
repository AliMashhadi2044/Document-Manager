
# ADR-0009 — نسخه‌بندی سند برای بازگشایی و اصلاح

**وضعیت:** پذیرفته · **تاریخ:** فاز ۰

## زمینه

پرامپت دو چیز متمایز می‌خواهد:

1. «چه کسی چه چیزی را کِی عوض کرد» — تاریخچه تغییرات فیلدی.
2. «اطلاعات تاریخی و گزارش‌های نسخه قبلی قابل بازیابی باشند» و صریحاً:
   «صرفاً ثبت یک log متنی بدون حفظ اطلاعات لازم برای بازسازی وضعیت قبلی کافی نیست».

این دو نیاز با یک مکانیزم برآورده نمی‌شوند: audit log فیلدی برای بازسازی کل aggregate
ناکافی است (باید همه تغییرات را معکوس بازپخش کرد که شکننده است)، و snapshot کامل برای
پاسخ به «کدام فیلد عوض شد» ناکارآمد است.

## تصمیم

**هر دو**، با نقش‌های جدا:

| مکانیزم | محتوا | کِی نوشته می‌شود | پاسخ به |
|---|---|---|---|
| `audit_logs` | `before`, `after`, `changed_fields`, `reason`, actor, trace | هر تغییر | «چه کسی چه چیزی را کِی عوض کرد» |
| `document_revisions` | snapshot **کامل** JSON از aggregate سند + `schema_version` | ثبت نهایی، بازگشایی، بایگانی، اصلاح | «سند در آن لحظه دقیقاً چه بود» |

`document_revisions.snapshot` شامل: سند، فراداده ستاد، همه فاکتورها، اقلام، ردیف‌های
سوخت، جزئیات انشعابات، پرداخت‌ها، و snapshotهای فروشنده و خریدار.

`report_runs` هم `version_id` قالب و هم `document_revision_id` را ثبت می‌کند → خروجی
تاریخی **قابل بازتولید** است.

## دلایل

- **بازیابی واقعی.** بازگشایی سند، پیش از هر تغییری یک نسخه با `trigger = 'REOPEN'`
  می‌سازد؛ پس وضعیت پیش از اصلاح همیشه یک `SELECT` فاصله دارد، نه یک بازپخش معکوس.
- **خروجی تاریخی معنادار.** گزارشی که سه ماه پیش چاپ شده، به نسخه سند و نسخه قالب همان
  زمان بسته است. تغییر بعدی سند، معنای آن خروجی را عوض نمی‌کند.
- **JSON اینجا درست است.** هدف بازسازی است، نه کوئری. این **تنها** استثنای قاعده
  «داده ساختارمند، نه JSON» است و دلیلش صریح است ([ADR-0005](ADR-0005-snapshot-tables.md)).

## جایگزین‌های رد‌شده

| جایگزین | دلیل رد |
|---|---|
| فقط audit log فیلدی | بازسازی وضعیت کامل شکننده و پرخطا؛ خلاف الزام صریح پرامپت |
| Event Sourcing کامل | پیچیدگی بزرگ برای کل دامنه، وقتی فقط سند به بازسازی نیاز دارد |
| جداول تاریخی برای هر موجودیت (SCD-2) | هر کوئری معمولی را پیچیده می‌کند؛ هزینه فراگیر برای نیاز موضعی |
| کپی کل سند در جداول `*_history` | همان حجم، بدون مزیت نسبت به JSON، با هزینه migration برای هر تغییر schema |
| فقط snapshot، بدون audit فیلدی | پاسخ به «کدام فیلد عوض شد» گران و غیرمستقیم می‌شود |

## پیامدها

- حجم: snapshot برای سند بزرگ چند صد کیلوبایت است. با `jsonb` و فشرده‌سازی TOAST
  قابل قبول؛ در فاز ۹ سیاست retention بررسی می‌شود.
- `schema_version` اجباری است و خواننده باید نسخه‌های قدیمی را تفسیر کند → یک تابع
  مهاجرت نسخه snapshot در `packages/shared` با تست.
- یک تابع سریالایز **واحد** برای ساخت snapshot وجود دارد؛ اگر فیلدی به مدل اضافه شود و
  در snapshot نیاید، تست «رفت‌و‌برگشت snapshot» ناموفق می‌شود.
- snapshot حاوی داده حساس (شبا، شناسه ملی) است → دسترسی به نسخه‌ها مجوزدار
  (`document:read_history`) و خارج از log عمومی.
