# ۱۸ — راهنمای بهره‌برداری و انتشار

این سند برای کسی نوشته شده که سامانه را **مستقر و نگهداری** می‌کند، نه برای کسی که
کدش را می‌نویسد. هر دستور در این سند روی همین مخزن اجرا و نتیجه‌اش دیده شده است.

---

## ۱. معماری استقرار

یک کانتینر، شامل هر دو بخش:

```
┌──────────────────────────────────────────┐
│  dm-app  (Dockerfile)                    │
│                                          │
│  Node 24 + NestJS   ← /api/v1/*          │
│  فایل‌های ساخته‌شده رابط  ← بقیه مسیرها  │
│  Chromium (تولید PDF)                    │
└──────────────────────────────────────────┘
        │                      │
        ▼                      ▼
   PostgreSQL 16         فضای ذخیره‌سازی S3
   (داده و حسابرسی)      (اسکن اسناد، خروجی‌های صف‌شده)
```

رابط وب از **همان origin** سرو می‌شود. نتیجه‌اش این است که کوکی نشست cross-site
نیست، CORS لازم نیست، و یک reverse proxy جداگانه برای کارکرد سامانه ضروری نیست
(برای TLS همچنان لازم است).

قلم فارسی **درون خروجی گزارش** جاسازی می‌شود، پس تصویر به قلم‌های نصب‌شده روی سرور
وابسته نیست و PDF روی هر ماشینی یکسان درمی‌آید.

---

## ۲. ساخت و اجرا

```bash
docker build -t dm-app:latest .
```

```bash
docker run -d --name dm-app \
  -p 3100:3100 \
  -e DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/document_manager?schema=public' \
  -e SESSION_SECRET="$(node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))")" \
  -e SEED_ADMIN_PASSWORD='<رمز اولیه مدیر>' \
  -e S3_ENDPOINT='http://storage:9000' \
  -e S3_ACCESS_KEY='...' -e S3_SECRET_KEY='...' -e S3_BUCKET='dm-documents' \
  -e RUN_MIGRATIONS=true \
  -e RUN_SEED=true \
  dm-app:latest
```

### متغیرهای کلیدی

| متغیر | اجباری | توضیح |
|---|:---:|---|
| `DATABASE_URL` | بله | اتصال PostgreSQL |
| `SESSION_SECRET` | بله | حداقل ۳۲ نویسه تصادفی؛ **برای هر محیط جداگانه** |
| `SEED_ADMIN_PASSWORD` | هنگام `RUN_SEED` | در production مقدار پیش‌فرض پذیرفته نمی‌شود |
| `RUN_MIGRATIONS` | خیر | `true` یعنی مهاجرت‌ها پیش از بالا آمدن اجرا شوند |
| `RUN_SEED` | خیر | داده مرجع (مجوز، نقش، فصل، قالب گزارش) — idempotent |
| `S3_*` | برای پیوست و خروجی صف‌شده | بدون آن، آپلود و خروجی صف‌شده کار نمی‌کنند |
| `EXPOSE_QUERY_COUNT` | خیر | ابزار تشخیصی؛ سرویس در production با `true` بالا نمی‌آید |

> **استقرار چندنمونه‌ای:** `RUN_MIGRATIONS=true` را فقط روی یک نمونه (یا یک کار
> جداگانه پیش از استقرار) روشن کنید. اجرای هم‌زمان مهاجرت از چند نمونه، درست نیست.

### سلامت سرویس

`GET /api/v1/health` — همان مسیری که `HEALTHCHECK` تصویر استفاده می‌کند. برای
متعادل‌کننده بار نیز همین مسیر است.

## ۳. پشتیبان‌گیری

### چه چیزی باید پشتیبان گرفته شود

| مورد | ابزار | توجه |
|---|---|---|
| پایگاه داده | `npm run backup` (`pg_dump -Fc`) | شامل همه داده و حسابرسی |
| فضای ذخیره‌سازی S3 | ابزار همان سرویس (مثلاً `mc mirror`) | **در پشتیبان پایگاه داده نیست** |
| متغیرهای محیطی | مدیریت راز سازمان | `SESSION_SECRET` و کلیدهای S3 |

پشتیبانِ تنهای پایگاه داده، سامانه را کامل برنمی‌گرداند: ارجاع فایل‌ها در پایگاه
داده می‌ماند ولی خود فایل اسکن در S3 است.

```bash
PG_CONTAINER=dm-postgres npm run backup      # محیط توسعه با postgres داخل Docker
DATABASE_URL=... npm run backup              # محیطی که کلاینت postgres نصب دارد
```

خروجی در `backups/` با نام `<database>-<تاریخ>-<ساعت>.dump` ساخته می‌شود. قالب
`custom` است تا بازیابی گزینشی و موازی ممکن باشد.

### آزمون بازیابی — اجباری و دوره‌ای

```bash
PG_CONTAINER=dm-postgres npm run restore:test
```

این اسکریپت پشتیبان می‌گیرد، در یک **پایگاه داده موقت** بازیابی می‌کند، و نتیجه را
با مبدأ مقایسه می‌کند: هم تعداد ردیف‌ها و هم **جمع مبالغ** جدول‌های مالی. پایگاه
داده موقت در پایان همیشه حذف می‌شود.

مقایسه جمع مبالغ عمدی است: بازیابی ناقصِ یک ستون `BIGINT` می‌تواند تعداد ردیف درست
و مبلغ غلط بدهد — بدترین حالت ممکن برای یک سامانه مالی.

**آخرین اجرای واقعی (فاز ۹):**

```

  OK   invoices               96 ردیف / جمع 9007200658952708  →  96 ردیف / جمع 9007200658952708
  OK   invoice_items          100 ردیف / جمع 9007200658952708  →  100 ردیف / جمع 9007200658952708
  OK   vendors                11  →  11
  OK   users                  4  →  4

```

جمع ۹٬۰۰۷٬۲۰۰٬۶۵۸٬۹۵۲٬۷۰۸ ریال از ۲^۵۳ بزرگ‌تر است؛ یعنی مسیر پشتیبان‌گیری و
بازیابی، صحت مبالغ بزرگ را هم حفظ می‌کند.

### بازیابی واقعی (روز حادثه)

```bash
# ۱. سرویس را متوقف کنید تا کسی روی داده نیم‌بازیابی‌شده کار نکند
docker stop dm-app

# ۲. پایگاه داده خالی بسازید
createdb -h HOST -U USER document_manager_restored

# ۳. بازیابی — exit-on-error عمدی است
pg_restore -h HOST -U USER -d document_manager_restored \
  --no-owner --no-privileges --exit-on-error backups/<فایل>.dump

# ۴. فایل‌های S3 را از پشتیبان همان بازه برگردانید

# ۵. DATABASE_URL را به پایگاه داده بازیابی‌شده بدهید و سرویس را بالا بیاورید
```

پس از بالا آمدن، دست‌کم این سه را دستی ببینید: ورود، باز شدن یک سند بایگانی‌شده
به‌همراه فایل پیوستش، و تولید یک گزارش مالیات.

## ۴. به‌روزرسانی نسخه

```bash
docker build -t dm-app:<نسخه> .
PG_CONTAINER=... npm run backup          # پیش از هر مهاجرت
docker stop dm-app && docker rm dm-app
docker run -d ... -e RUN_MIGRATIONS=true dm-app:<نسخه>
```

مهاجرت‌ها رو به جلو هستند. بازگشت به نسخه قبلی **پس از** اجرای یک مهاجرت، نیازمند
بازیابی پشتیبان است؛ به همین دلیل گرفتن پشتیبان پیش از استقرار اختیاری نیست.

## ۵. پایش

| چه چیزی | از کجا | چرا |
|---|---|---|
| سلامت | `GET /api/v1/health` | زنده بودن سرویس و اتصال پایگاه داده |
| خطاها | log سرویس (JSON، pino) | هر خطا `traceId` دارد که به کاربر هم نشان داده می‌شود |
| حسابرسی | جدول `audit_logs` | عملیات حساس: ثبت نهایی، بایگانی، خروجی، تغییر دسترسی |
| خروجی‌های صف‌شده | جدول `export_jobs` | کارهای مانده در `RUNNING` نشانه راه‌اندازی مجدد ناتمام‌اند |

هنگام گزارش خطا از کاربر، `traceId` را بخواهید: همان شناسه در log سرویس هست و
مسیر، متد و کد خطا را می‌دهد — بدون اینکه داده حساس در پیام کاربر باشد.

## ۶. چک‌لیست تحویل

پیش از تحویل به بهره‌بردار:

- [ ] `npm run ci:full` سبز (ساخت، نوع، lint، واحد، E2E)
- [ ] `npm run verify:phase9` بدون رد (چک‌لیست امنیتی)
- [ ] `npm run perf:phase9` و ثبت اعداد در `docs/19-performance.md`
- [ ] `npm run restore:test` روی همان پایگاه داده‌ای که به production می‌رود
- [ ] `SESSION_SECRET` تازه و منحصر‌به‌فرد برای این محیط ساخته شده
- [ ] رمز اولیه مدیر عوض شده و در مدیریت راز سازمان ثبت شده
- [ ] `EXPOSE_QUERY_COUNT` تنظیم نشده یا `false` است
- [ ] پشتیبان‌گیری زمان‌بندی‌شده (پایگاه داده **و** S3) فعال است
- [ ] یک بازیابی آزمایشی از پشتیبان همان زمان‌بندی انجام شده
- [ ] TLS جلوی سرویس برقرار است (کوکی نشست `Secure` می‌شود)
- [ ] کاربران واقعی با نقش درست ساخته شده‌اند و کاربران آزمون حذف شده‌اند
